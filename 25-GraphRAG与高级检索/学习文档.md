# 第25节：GraphRAG 与高级检索 — 知识图谱增强、多跳检索

## 一、向量检索的天花板：多跳推理问题

向量检索擅长"语义相似度匹配"，回答"和这句话意思相近的内容在哪"这类问题很在行。但它不擅长处理需要**跨文档关系推理**的问题：

```
问题："哪些人同时投资过 A 公司和 B 公司？"

这个答案不存在于任何单一文档里，而是需要：
1. 从文档集合中找出"谁投资了 A 公司"（可能分散在多份公告里）
2. 找出"谁投资了 B 公司"（同样分散）
3. 求两个集合的交集

向量检索一次调用只能召回"语义上最像这个问题"的一批文档，
但这个问题本身在语义上并不指向任何具体文档，
它指向的是"实体之间的关系结构"——这正是向量空间里缺失的维度。
```

这类问题统称**多跳问题（Multi-hop Question）**，是纯向量 RAG 的天花板。

## 二、GraphRAG 的核心思路

GraphRAG 不再把文档打散成孤立的向量塞进一个"大池子"里，而是先**显式抽取实体和关系，构建成知识图谱**，再基于图结构做查询。

### 2.1 知识图谱的基本组成

```python
from pydantic import BaseModel

class Entity(BaseModel):
    """图谱中的节点"""
    name: str
    entity_type: str  # 如 "人物"、"公司"、"产品"

class Relation(BaseModel):
    """图谱中的边"""
    source: str       # 起始实体名
    target: str       # 目标实体名
    relation_type: str  # 如 "投资了"、"任职于"、"收购了"
    evidence: str      # 支撑这条关系的原文片段（用于溯源）

class KnowledgeTriple(BaseModel):
    """一条完整的三元组：实体-关系-实体"""
    entity: Entity
    relation: Relation
    target_entity: Entity
```

### 2.2 用 LLM 做实体关系抽取

```python
from pydantic import BaseModel

class ExtractionResult(BaseModel):
    entities: list[Entity]
    relations: list[Relation]

def extract_graph_from_chunk(llm, chunk_text: str) -> ExtractionResult:
    """用结构化输出（阶段1学过的技术）让 LLM 从文本块中抽取实体和关系"""
    prompt = f"""从以下文本中抽取所有实体（人物、公司、产品等）和它们之间的关系。

文本：
{chunk_text}

请按照 JSON Schema 输出实体列表和关系列表，关系要包含支撑证据原文。"""

    response = llm.with_structured_output(ExtractionResult).invoke(prompt)
    return response
```

### 2.3 实体消歧（Entity Resolution）—— 图谱质量的生死线

不同文档里同一个实体可能有不同的写法："张三""张先生""Zhang San"如果被识别成三个独立节点，图就是错的：

```python
def merge_duplicate_entities(entities: list[Entity], llm) -> dict[str, str]:

    用 LLM 或规则判断哪些实体名指向同一个真实实体，
    返回一个"别名 -> 标准名"的映射表
    """
```

**面试考点**：实体消歧没做好，图谱质量再高的抽取模型也救不回来，这是 GraphRAG 项目里最容易被低估、但实际影响最大的一环。

## 三、微软 GraphRAG 的完整流程

微软 2024 年发布的 GraphRAG 是这个方向的标杆实现，核心流程分五步：

```
1. 文档切块
   ↓
2. 用 LLM 对每一块做实体关系抽取（三元组）
   ↓
3. 实体消歧与合并，构建统一的知识图谱
   ↓
4. 在图上做社区检测（Community Detection），把关系紧密的
   实体聚类成"社区"（比如同一个行业内互相关联的公司）
   ↓
5. 用 LLM 给每个社区生成摘要，形成"社区摘要索引"
```

### 3.1 局部查询 vs 全局查询

GraphRAG 支持两种截然不同的查询模式，这是它相比向量 RAG 最大的差异化能力：

```python
class GraphRAGQueryEngine:
    def __init__(self, graph, community_summaries, vector_index):
        self.graph = graph
        self.community_summaries = community_summaries
        self.vector_index = vector_index

    def local_query(self, entity_name: str, question: str, hops: int = 2) -> str:
        """局部查询：从具体实体出发，做多跳图遍历，回答关于个别实体的具体问题"""
        subgraph = self.graph.get_neighborhood(entity_name, max_hops=hops)
        context = self._format_subgraph_as_text(subgraph)
        return llm.invoke(f"根据以下实体关系回答问题：\n{context}\n问题：{question}")

    def global_query(self, question: str) -> str:
        """全局查询：直接在社区摘要上检索，回答需要俯瞰全局的问题
        （比如"整个数据集里主要的商业合作趋势是什么"）
        这是向量检索完全做不到的能力——因为答案不来自任何单一文档，
        而是来自对大量关系的宏观归纳。"""
        relevant_summaries = self.vector_index.search(question, top_k=5, index="community_summaries")
        context = "\n\n".join(relevant_summaries)
        return llm.invoke(f"根据以下社区摘要回答问题：\n{context}\n问题：{question}")

    def _format_subgraph_as_text(self, subgraph) -> str:
        lines = []
        for relation in subgraph.relations:
            lines.append(f"{relation.source} --{relation.relation_type}--> {relation.target}"
                          f"（依据：{relation.evidence}）")
        return "\n".join(lines)
```

### 3.2 多跳图遍历示例：回答开篇的投资问题

```python
def find_common_investors(graph, company_a: str, company_b: str) -> list[str]:
    """图遍历天然支持多跳查询：这是向量检索做不到、但图结构轻松解决的问题"""
    investors_a = set(graph.get_source_nodes(target=company_a, relation_type="投资了"))
    investors_b = set(graph.get_source_nodes(target=company_b, relation_type="投资了"))
    return list(investors_a & investors_b)  # 集合交集，一步到位
```

## 四、GraphRAG 的代价与工程取舍

### 4.1 构建成本

| 环节 | 成本来源 |
|------|----------|
| 实体关系抽取 | 每个文档块都要过一次 LLM 调用，文档量大时成本线性增长 |
| 实体消歧 | 需要额外的 LLM 调用或规则引擎做别名合并 |
| 社区检测与摘要 | 社区数量多时，摘要生成也是一笔不小的 LLM 调用开销 |
| 图谱维护 | 文档更新后，图谱的增量更新比向量库的增量更新复杂得多 |

### 4.2 什么时候该用 GraphRAG，什么时候不该用

```python
def should_use_graph_rag(business_context: dict) -> bool:
    """决策辅助：是否值得引入 GraphRAG"""
    has_relational_queries = business_context.get("relational_query_ratio", 0) > 0.15
    # 业务中超过 15% 的查询涉及"关系推理"（比如"谁和谁有关联"），
    # 这个比例可以通过分析历史查询日志或用户调研得到

    document_scale_acceptable = business_context.get("doc_count", 0) < 100_000
    # 图构建成本会随文档量快速增长，超大规模语料构建图谱可能不划算

    can_afford_maintenance = business_context.get("has_ongoing_llm_budget", False)
    # 图谱不是一次性构建就完事，文档持续更新意味着持续的构建成本

    return has_relational_queries and document_scale_acceptable and can_afford_maintenance
```

**面试标准答法**：GraphRAG 不是向量 RAG 的替代品，而是针对"多跳关系推理"这个特定短板的补丁。选型依据是业务里有没有真实存在、高频出现的关系型查询需求，而不是因为"GraphRAG 听起来更先进"就无脑上马。

## 五、混合架构：向量检索 + 图查询并存

现实中更常见的做法不是非黑即白选一个，而是用路由层决定每个查询该走哪条路径：

```python
from enum import Enum

class QueryRoute(str, Enum):
    VECTOR = "vector"       # 语义相似度查询
    GRAPH_LOCAL = "graph_local"    # 单实体多跳查询
    GRAPH_GLOBAL = "graph_global"  # 全局归纳类查询
    HYBRID = "hybrid"       # 两者都需要

def route_query(llm, question: str) -> QueryRoute:
    """用轻量的意图识别判断查询该走哪条检索路径"""
    prompt = f"""判断以下问题的检索方式：
- 如果是查找具体信息或相似内容，返回 vector
- 如果是查询实体之间的关系（谁和谁有关联），返回 graph_local
- 如果是需要归纳整个数据集趋势的宏观问题，返回 graph_global
- 如果两者都需要，返回 hybrid

问题：{question}
只返回上述四个词之一。"""
    response = llm.invoke(prompt)
    return QueryRoute(response.content.strip().lower())


class HybridRAGSystem:
    def __init__(self, vector_pipeline, graph_engine, llm):
        self.vector_pipeline = vector_pipeline
        self.graph_engine = graph_engine
        self.llm = llm

    def answer(self, question: str) -> str:
        route = route_query(self.llm, question)

        if route == QueryRoute.VECTOR:
            context = self.vector_pipeline.retrieve(question)
        elif route == QueryRoute.GRAPH_LOCAL:
            entity = self._extract_main_entity(question)
            context = self.graph_engine.local_query(entity, question)
        elif route == QueryRoute.GRAPH_GLOBAL:
            context = self.graph_engine.global_query(question)
        else:  # HYBRID
            vector_context = self.vector_pipeline.retrieve(question)
            graph_context = self.graph_engine.global_query(question)
            context = f"{vector_context}\n\n{graph_context}"

        return self.llm.invoke(f"根据以下资料回答问题：\n{context}\n问题：{question}")

    def _extract_main_entity(self, question: str) -> str:
        response = self.llm.invoke(f"从这个问题中提取核心的实体名称，只返回名称：{question}")
        return response.content.strip()
```

## 六、面试高频问答

**Q：GraphRAG 和普通 RAG 的本质区别是什么？**
A：普通 RAG 检索的单位是"文本块"，依赖向量相似度；GraphRAG 检索的单位是"实体和关系"，依赖图遍历。前者擅长语义相似问题，后者擅长关系推理和跨文档归纳问题。

**Q：GraphRAG 的全局查询为什么向量检索做不到？**
A：全局查询的答案（比如"数据集里的主要趋势"）不对应任何单一文档，而是对大量分散信息的宏观归纳。向量检索的召回逻辑是"找最相似的几条"，天然无法覆盖"综合全局所有信息"这种诉求；而 GraphRAG 通过社区摘要提前把归纳工作做在了索引构建阶段。

**Q：如果图谱构建质量不高，会有什么后果，怎么补救？**
A：实体消歧不准会导致图谱里出现大量重复或断裂的节点，图遍历得到错误或不完整的结果。补救手段包括人工审核高频实体的合并结果、引入更强的消歧模型、以及在关系上保留原文证据方便人工核查和事后修正。

### 面试模拟

## 八、小结

这一节讲清楚了 GraphRAG 存在的意义：向量检索擅长语义相似度匹配，但在多跳关系推理和全局归纳问题上有天花板，GraphRAG 通过显式构建实体关系图、支持局部和全局两种查询模式补上了这块短板，代价是图构建和维护成本高、质量依赖实体消歧的准确率。工程上更现实的做法是向量检索和图查询并存的混合架构，用路由层按问题类型分发到合适的检索路径，而不是所有查询都走最贵的那条路。
