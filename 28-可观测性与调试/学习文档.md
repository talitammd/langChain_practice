# 第28节：可观测性与调试 — 生产环境里 Agent 出了问题怎么查

## 一、可观测性 vs Eval：两个互补但不同的问题

| | Eval | 可观测性（Observability） |
|---|------|------|
| 回答的问题 | 这个系统整体上好不好 | 刚才这一次具体执行发生了什么 |
| 时机 | 离线、批量、发布前 | 在线、逐条、发布后 |
| 用途 | 决定要不要发布这个版本 | 决定出问题后怎么快速定位、能否精确复现 |

Agent 系统的执行路径是**动态生成**的——同一个输入，Agent 可能因为模型的非确定性走出完全不同的分支（调用不同的工具、检索到不同的证据）。这和传统后端系统"执行路径确定、只是数据不同"有本质区别，这正是可观测性对 Agent 工程师是必修课的原因。

## 二、核心概念：分布式追踪（Tracing）

### 2.1 Trace 和 Span

一次 Agent 的完整执行被记录成一棵调用树：

```
Trace（一次完整请求）
├── Span: 用户问题理解与路由判断
│   └── LLM 调用：意图分类
├── Span: 检索阶段
│   ├── LLM 调用：生成检索关键词
│   ├── 向量检索
│   └── 重排序
├── Span: 工具调用
│   └── 调用外部 API：查询订单状态
└── Span: 生成最终回答
    └── LLM 调用：结构化输出生成
```

每个 span 记录：输入、输出、耗时、token 消耗、是否出错。

### 2.2 用代码实现一个简化的 Tracing 系统

```python
import time
import uuid
from dataclasses import dataclass, field
from contextlib import contextmanager


@dataclass
class Span:
    span_id: str
    name: str
    span_type: str  # "llm_call" / "tool_call" / "retrieval" / "reasoning"
    start_time: float
    end_time: float | None = None
    input_data: dict = field(default_factory=dict)
    output_data: dict = field(default_factory=dict)
    token_usage: dict = field(default_factory=dict)
    error: str | None = None
    children: list["Span"] = field(default_factory=list)

    @property
    def duration_ms(self) -> float:
        if self.end_time is None:
            return 0.0
        return (self.end_time - self.start_time) * 1000


@dataclass
class Trace:
    trace_id: str
    root_span: Span
    metadata: dict = field(default_factory=dict)


class Tracer:
    """一个简化的追踪器，用栈维护当前的 span 嵌套关系"""

    def __init__(self):
        self._span_stack: list[Span] = []
        self.current_trace: Trace | None = None

    def start_trace(self, name: str, metadata: dict | None = None) -> Trace:
        root_span = Span(span_id=str(uuid.uuid4()), name=name, span_type="trace_root",
                          start_time=time.time())
        self.current_trace = Trace(trace_id=str(uuid.uuid4()), root_span=root_span,
                                     metadata=metadata or {})
        self._span_stack = [root_span]
        return self.current_trace

    @contextmanager
    def span(self, name: str, span_type: str, input_data: dict | None = None):
        """用上下文管理器包裹一段操作，自动记录耗时和嵌套关系"""
        new_span = Span(
            span_id=str(uuid.uuid4()), name=name, span_type=span_type,
            start_time=time.time(), input_data=input_data or {},
        )
        parent = self._span_stack[-1]
        parent.children.append(new_span)
        self._span_stack.append(new_span)

        try:
            yield new_span
        except Exception as e:
            new_span.error = str(e)
            raise
        finally:
            new_span.end_time = time.time()
            self._span_stack.pop()

    def finish_trace(self) -> Trace:
        self.current_trace.root_span.end_time = time.time()
        return self.current_trace


# 使用示例
tracer = Tracer()
tracer.start_trace("用户问题处理", metadata={"user_id": "u123"})

with tracer.span("路由判断", "reasoning", {"question": "红烧肉怎么做"}) as span:
    route = "semantic"
    span.output_data = {"route": route}

with tracer.span("向量检索", "retrieval", {"query": "红烧肉做法"}) as span:
    results = ["检索结果1", "检索结果2"]
    span.output_data = {"num_results": len(results)}

with tracer.span("生成回答", "llm_call", {"prompt_tokens": 500}) as span:
    answer = "红烧肉的做法是..."
    span.token_usage = {"prompt_tokens": 500, "completion_tokens": 150}
    span.output_data = {"answer": answer}

trace = tracer.finish_trace()
print(f"整体耗时：{trace.root_span.duration_ms:.1f}ms")
for child in trace.root_span.children:
    print(f"  {child.name}: {child.duration_ms:.1f}ms")
```

## 三、OpenTelemetry GenAI 语义规范（2026 行业标准）

### 3.1 为什么需要统一标准

以前每家可观测性平台（LangSmith、Braintrust、Datadog）的数据格式都不一样，接入哪个平台就要绑定它专属的 SDK，迁移成本极高。OpenTelemetry 针对生成式 AI 推出的语义规范（GenAI Semantic Conventions）统一定义了记录 LLM 调用应包含的标准字段：

```python
# 遵循 OpenTelemetry GenAI 语义规范的标准字段命名示例
STANDARD_LLM_SPAN_ATTRIBUTES = {
    "gen_ai.system": "openai",              # 使用的模型提供方
    "gen_ai.request.model": "gpt-4o",       # 请求的模型名称
    "gen_ai.request.temperature": 0.7,      # 采样温度
    "gen_ai.request.max_tokens": 2048,      # 最大生成长度
    "gen_ai.usage.prompt_tokens": 500,      # 输入 token 消耗
    "gen_ai.usage.completion_tokens": 150,  # 输出 token 消耗
    "gen_ai.response.finish_reason": "stop",  # 结束原因
}

# 用标准字段记录 span，好处是这份数据可以在支持该规范的
# 任意可观测性平台之间自由迁移，不会被某一家厂商的私有格式锁死
```

**面试考点**：这是行业走向成熟的标志性事件——统一标准降低了工具链切换成本，也让团队可以自由组合"用 A 厂商做 tracing 收集，用 B 厂商做可视化分析"，不再被单一供应商绑定。

## 四、结构化日志：粒度和脱敏

### 4.1 反面示例：无结构日志

```python
# 反面教材：出问题时几乎无法排查
logger.info("调用成功")
logger.error("调用失败")
```

### 4.2 结构化记录的正确做法

```python
import json
import re
from datetime import datetime


class StructuredLLMLogger:
    def __init__(self, sink):
        self.sink = sink  # 可以是文件、消息队列、日志平台的 SDK

    def log_llm_call(
        self, trace_id: str, prompt_template: str, variables: dict,
        model_output: str, duration_ms: float, token_usage: dict, error: str | None = None
    ) -> None:
        record = {
            "timestamp": datetime.utcnow().isoformat(),
            "trace_id": trace_id,
            "prompt_template": prompt_template,
            "variables": self._redact_pii(variables),  # 脱敏
            "model_output": model_output,
            "duration_ms": duration_ms,
            "token_usage": token_usage,
            "error": error,
        }
        self.sink.write(json.dumps(record, ensure_ascii=False))

    def _redact_pii(self, data: dict) -> dict:
        """脱敏处理：手机号、身份证号等敏感信息不能明文写入日志系统"""
        redacted = {}
        for key, value in data.items():
            if isinstance(value, str):
                value = re.sub(r'1[3-9]\d{9}', '[PHONE_REDACTED]', value)
                value = re.sub(r'\d{17}[\dXx]', '[ID_REDACTED]', value)
            redacted[key] = value
        return redacted
```

**面试考点**：企业级系统的日志脱敏不是可选项，是合规红线。哪些字段需要脱敏、脱敏规则怎么维护，是面试官考察工程严谨性的常见切入点。

## 五、会话重放（Replay）：精确复现非确定性问题

### 5.1 为什么不能简单地"重新跑一遍"

Agent 系统是非确定的，线上出问题后，用同样的输入在本地重新调用真实模型，得到的输出可能完全不同——问题可能就复现不出来了。

### 5.2 完整记录执行快照，离线回放

```python
from dataclasses import dataclass, asdict
import json


@dataclass
class ExecutionSnapshot:
    """完整记录一次执行的所有输入输出，包括每一步工具调用的真实返回结果"""
    trace_id: str
    initial_input: str
    llm_calls: list[dict]     # 每次 LLM 调用的 prompt 和 response
    tool_calls: list[dict]    # 每次工具调用的参数和真实返回结果
    final_output: str


class ReplayableAgent:
    """支持从快照回放的 Agent 包装器：回放模式下不调用真实模型/工具，
    而是按记录顺序返回快照里保存的结果，保证复现的是精确的那次异常路径"""

    def __init__(self, real_llm, real_tools):
        self.real_llm = real_llm
        self.real_tools = real_tools
        self.replay_mode = False
        self.snapshot: ExecutionSnapshot | None = None
        self._llm_call_index = 0
        self._tool_call_index = 0

    def load_snapshot(self, snapshot: ExecutionSnapshot) -> None:
        self.replay_mode = True
        self.snapshot = snapshot
        self._llm_call_index = 0
        self._tool_call_index = 0

    def call_llm(self, prompt: str) -> str:
        if self.replay_mode:
            # 回放模式：直接返回快照里记录的历史响应，不真的调用模型
            recorded = self.snapshot.llm_calls[self._llm_call_index]
            self._llm_call_index += 1
            return recorded["response"]
        return self.real_llm.invoke(prompt)

    def call_tool(self, tool_name: str, args: dict):
        if self.replay_mode:
            recorded = self.snapshot.tool_calls[self._tool_call_index]
            self._tool_call_index += 1
            return recorded["result"]
        return self.real_tools[tool_name](**args)


def save_snapshot(trace: Trace, final_output: str) -> ExecutionSnapshot:
    """从一次真实执行的 trace 中提取快照，用于后续离线回放"""
    llm_calls, tool_calls = [], []

    def walk(span: Span):
        if span.span_type == "llm_call":
            llm_calls.append({"prompt": span.input_data, "response": span.output_data})
        elif span.span_type == "tool_call":
            tool_calls.append({"args": span.input_data, "result": span.output_data})
        for child in span.children:
            walk(child)

    walk(trace.root_span)
    return ExecutionSnapshot(
        trace_id=trace.trace_id,
        initial_input=trace.metadata.get("input", ""),
        llm_calls=llm_calls,
        tool_calls=tool_calls,
        final_output=final_output,
    )
```

**工程价值**：排查生产问题时，工程师可以在本地 IDE 里打断点、单步调试，加载的是这次线上真实出问题的执行快照，而不是一个新的、可能完全不同的随机结果，这是调试非确定性系统的核心手段。

## 六、主动告警机制

有可观测性数据但没人主动看等于没有。核心监控指标：

```python
from dataclasses import dataclass


@dataclass
class AlertThresholds:
    max_error_rate: float = 0.05          # 错误率超过 5% 告警
    max_p99_latency_ms: float = 5000      # P99 延迟超过 5 秒告警
    max_token_cost_increase_pct: float = 0.5  # token 消耗环比增长超过 50% 告警
    max_refusal_rate: float = 0.15        # "拒绝回答"比例超过 15% 告警（可能是检索出了问题）


class ProductionMonitor:
    def __init__(self, thresholds: AlertThresholds, alert_sink):
        self.thresholds = thresholds
        self.alert_sink = alert_sink

    def check_metrics(self, current_metrics: dict) -> list[str]:
        alerts = []
        if current_metrics["error_rate"] > self.thresholds.max_error_rate:
            alerts.append(f"错误率异常：{current_metrics['error_rate']:.1%}")
        if current_metrics["p99_latency_ms"] > self.thresholds.max_p99_latency_ms:
            alerts.append(f"P99 延迟异常：{current_metrics['p99_latency_ms']:.0f}ms")
        if current_metrics["refusal_rate"] > self.thresholds.max_refusal_rate:
            # 拒绝回答比例突然升高，往往意味着检索系统出了问题
            # （比如向量库连不上，导致大量查询检索不到证据只能拒答）
            alerts.append(f"拒绝回答比例异常：{current_metrics['refusal_rate']:.1%}，"
                          f"请检查检索链路是否正常")

        for alert in alerts:
            self.alert_sink.send(alert)
        return alerts
```

## 七、面试高频问答

**Q：Eval 和可观测性，先做哪个？**
A：两者应该同时规划，但优先级上可观测性是生产系统的生命线——没有它，线上出了问题完全没法排查；Eval 是质量提升的方法论——没有它，无法证明每次改动是变好还是变坏。成熟团队两者都不能少，但资源有限时先把可观测性的基本追踪能力搭起来，保证系统"出问题能被看见"。

**Q：为什么 Agent 系统的调试比传统后端难？**
A：传统后端出问题，同样的输入本地重跑大概率能复现；Agent 系统因为模型的非确定性，同样输入两次调用可能走完全不同的路径，必须靠完整记录执行快照、离线回放的方式才能精确复现某次特定的异常执行。

**Q：OpenTelemetry GenAI 语义规范解决了什么实际问题？**
A：统一了不同可观测性平台之间的数据格式标准，避免团队被某一家供应商的私有 SDK 锁死，也让"多个可观测性工具组合使用"变得可行。

## 八、练习题

### 概念理解

1. 为什么 Agent 系统需要"会话重放"而不能简单地用同样输入重新调用系统来复现问题？
2. 日志脱敏应该在写入日志之前做还是之后做？为什么？
3. "拒绝回答比例突然升高"这个告警信号，可能对应哪些不同的根因？

### 动手编码

4. 完善本节的 `Tracer` 类，加入把 trace 导出成类似 Chrome DevTools 火焰图格式（或简单的 JSON 树状结构）的方法，方便可视化查看每个 span 的耗时占比。

5. 实现 `save_snapshot` 和 `ReplayableAgent` 的完整闭环：先跑一次"真实"的模拟 Agent 执行并保存快照，再加载快照做回放，验证两次的最终输出完全一致。

6. 给 `StructuredLLMLogger` 增加更多脱敏规则（邮箱地址、银行卡号等），并写一组测试用例验证脱敏的正确性和是否有误伤（比如把正常文本里的数字误判成敏感信息）。

### 面试模拟

7. "生产环境里，Agent 的回答质量突然下降，你怎么排查？" 参考答法：先看可观测性面板里的 RAGAS 类指标或错误率趋势，定位是从什么时间点开始异常，对照发布记录看是否有相关变更；再抽取该时间段内的几条异常 trace，逐层查看是路由错了、检索错了、还是生成阶段出了问题；最后用会话重放在本地复现，排查完加一条回归测试用例防止再犯。

8. "怎么设计 token 消耗异常告警，防止一次 bug 导致巨额账单？" 参考答法：设置分钟级和小时级两层监控，一旦 token 消耗速率相比历史基线出现异常陡增（比如陷入死循环导致大量重复调用），立即触发告警甚至自动熔断，这和第 17 节讲的 recursion_limit 是同一类问题的两层防护——一层在代码逻辑层面兜底，一层在生产监控层面兜底。

## 九、小结

这一节讲清楚了 Eval 之外同样重要的另一半——可观测性。核心是基于 OpenTelemetry GenAI 语义规范的分布式追踪，把每次执行记录成包含完整输入输出的调用树；结构化日志要注意粒度和脱敏；会话重放解决了非确定性系统"复现问题难"的核心痛点；主动告警机制保证问题能第一时间被发现而不是等用户投诉。Eval 决定要不要发布，可观测性决定发布后出了问题能多快定位、能不能精确复现。
