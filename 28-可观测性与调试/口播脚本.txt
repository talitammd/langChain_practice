凌晨两点，你的 Agent 在生产环境突然大量报错，用户投诉说回答文不对题，你打开日志一看，只有一行"调用失败"，没有任何上下文，你根本不知道 Agent 那一刻在想什么、调用了什么工具、检索到了什么证据。这种场景在传统后端开发里几乎不会发生，因为传统系统的执行路径是确定的，但 Agent 系统的执行路径是动态生成的，每一次运行可能走完全不同的分支，这就是为什么可观测性对 Agent 工程师来说是一门必修课。

先讲清楚可观测性和 Eval 的区别，很多人会把这两者搞混。Eval 回答的问题是"这个系统整体上好不好"，是离线的、批量的、面向系统改进的。可观测性回答的问题是"刚才这一次具体的执行发生了什么"，是在线的、逐条的、面向问题排查的。两者是互补关系，Eval 告诉你要不要发布这个版本，可观测性告诉你发布之后线上出了问题该怎么查。

可观测性的核心工具叫追踪，英文 tracing。一次 Agent 的完整执行会被记录成一棵调用树，最外层是整个请求的一次 trace，里面嵌套着一个个 span，每个 span 代表一个具体的操作单元——一次 LLM 调用、一次工具调用、一次向量检索，每个 span 都要记录输入、输出、耗时、以及消耗的 token 数量。有了这棵树，出问题的时候你能一眼看到是哪一步花的时间最长、哪一步返回的内容有异常，而不是对着一堆散落的日志大海捞针。

2026 年这个领域最重要的进展是 OpenTelemetry 推出了针对生成式 AI 的语义规范，业界简称 GenAI semantic conventions，它统一定义了记录 LLM 调用应该包含哪些标准字段，比如模型名称、prompt 内容、输出内容、token 消耗、温度参数这些。这件事的意义在于，以前每家可观测性平台的数据格式都不一样，接入哪个平台就要绑定它的 SDK，现在有了统一标准之后，你的追踪数据可以在不同平台之间自由迁移，不会被某一家厂商锁死，这是整个行业走向成熟的标志性事件。

除了 tracing，日志和结构化记录同样重要，但要讲究记录的粒度和格式。生产系统不能只打印一句"调用成功"或者"调用失败"，而要把每一次 LLM 调用的完整上下文——用了什么 prompt 模板、传了什么变量、模型返回了什么、耗时多久——都以结构化的方式记录下来，方便之后做查询和聚合分析。同时要注意脱敏，用户的隐私信息、企业的敏感数据不能直接明文写进日志系统。

调试环节还有一个专门针对 Agent 系统的技巧，叫会话重放，英文 replay。因为 Agent 的执行是非确定的，线上出问题之后，你没法简单地在本地用同样的输入跑一遍就复现问题，因为模型的输出可能这次和上次不一样。会话重放的做法是把生产环境里那次完整的执行记录——包括每一步的输入输出、每一次工具调用的返回结果——都保存下来，排查问题的时候直接加载这份记录在本地回放，而不是重新调用真实的模型和工具，这样才能保证复现的是精确的那次异常执行路径，而不是又跑出一个新的随机结果。

生产环境里还必须建立告警机制，光有可观测性数据但没人主动看是没用的。核心要监控的指标包括错误率、平均延迟、token 消耗异常增长、以及一些业务相关的信号，比如"拒绝回答"的比例突然升高，可能意味着检索系统出了问题导致大量查询检索不到相关证据。这些指标一旦超过阈值应该主动推送告警，而不是等用户投诉才知道系统出了问题。

面试标准答法：可观测性系统的核心是基于 OpenTelemetry GenAI 语义规范的分布式追踪，把每次执行记录成包含完整输入输出的调用树，配合结构化日志、会话重放能力和主动告警机制，这套体系是 Eval 之外保障生产系统稳定性的另一半，Eval 决定要不要发布，可观测性决定发布后出了问题多快能定位、能不能精确复现。下一节我们讲怎么把这套系统的运行成本降下来，怎么在保证质量的前提下做模型路由和延迟优化。
