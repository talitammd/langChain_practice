面试官给你一个场景："用户说帮我调研竞品、写一份分析报告、做成 PPT 发到邮箱。"你的 Agent 要怎么处理这个任务？如果你的答案是"用 ReAct 一步步来"，面试官会追一句——"那要是跑到第十步发现第三步的调研方向错了，你整个推倒重来？"这个问题就是在考你懂不懂规划与任务分解。上一节我们说了 ReAct 是逐步贪心的——每一步只看当前状态决定下一步，没有全局视野。这对简单任务够用，但一旦任务复杂到需要十几步甚至几十步，逐步贪心就会走弯路、死循环、或者跑偏了回不来。怎么办？给 Agent 加一个大脑——规划器。

这就是 Plan-and-Execute 架构的核心思想：先想清楚要做什么，再一步步去做，做的过程中还能回头调整计划。它把一个大任务拆成三个角色的协作：Planner 负责把大任务分解成有序的子任务列表；Executor 负责逐个执行子任务，每个子任务内部可以跑 ReAct 循环；Re-planner 负责在每个子任务执行完之后，根据实际结果判断要不要修改后续计划。

回到刚才那个场景：Planner 会把"调研竞品写报告做 PPT 发邮箱"拆成四个子任务——第一步搜索竞品信息，第二步整理成分析报告，第三步转成 PPT，第四步发送邮件。Executor 执行完第一步拿到搜索结果后，Re-planner 会看一眼："搜索结果够不够？要不要补充数据？"如果够了继续第二步，如果不够就动态插入一个"补充调研"的子任务。这就是 Replan 机制的价值——计划不是死的，是跟着执行结果动态调整的。

那面试官一定会追问：Plan-and-Execute 和 ReAct 到底什么关系？不是替代，是互补。你可以把它想成一个两层结构：外层是 Plan-and-Execute 管全局规划，内层是 ReAct 管单步执行。Planner 说"下一步该查天气"，怎么查、查哪个接口、参数怎么填，这些细节交给 Executor 里的 ReAct 循环去决定。就像公司里总监定方向、员工管执行，分工明确。

这里还有一个省钱的变体你得知道——ReWOO。全称 Reasoning Without Observation。它的思路更激进：Planner 一次性把所有子任务和它们的依赖关系全规划好，然后 Executor 按计划顺序执行，中间不再回去问大模型"下一步干什么"。每一步的输出用占位符传给下一步。好处是大幅减少 LLM 调用次数、压低 token 成本。坏处是计划一旦出错，Executor 不会自己修正——它是纯机械执行。所以 ReWOO 适合任务路径比较确定的场景，不确定性高的还是得用带 Replan 的 Plan-and-Execute。

那面试官最爱问的深度题是："如果任务特别复杂，子任务还能继续拆怎么办？"这就引出了层级规划——Hierarchical Planning。顶层 Planner 把大任务拆成几个阶段，每个阶段交给一个子 Planner 继续拆更细的步骤，最底层才是执行器。就像一棵任务树：根节点是总目标，中间节点是子目标，叶子节点是具体可执行的动作。这种思路在 Multi-Agent 系统里特别常见——Supervisor Agent 做顶层规划，Worker Agent 做子任务执行，天然的层级结构。

最后说一个很多人忽略但面试加分的点：规划本身也会出错。Planner 也是大模型，它可能把任务拆得不合理、遗漏步骤、或者搞错依赖顺序。成熟的方案会在 Replan 环节做"计划验证"——检查子任务之间的依赖是否合理、是否有遗漏、已完成的步骤结果是否满足后续需要。如果发现问题就触发重新规划。这就像项目管理里的 Sprint Review：做完一个迭代回头看看，方向对不对、要不要调整。

总结三句话带走。第一，Plan-and-Execute 把"想"和"做"分开——Planner 全局规划、Executor 逐步执行、Re-planner 动态调整，解决 ReAct 逐步贪心走弯路的问题。第二，ReWOO 是省成本变体，一次性规划完不回头，适合路径确定的任务；层级规划把子任务继续往下拆，适合特别复杂的长任务。第三，规划本身也会出错，所以要有 Replan 验证机制——计划不是死的，是跟着执行结果动态演进的。

下一节我们聊 Agent 的另一个核心能力——记忆系统。Planner 规划完了、Executor 执行了十几步，中间产生的信息怎么存、怎么取、怎么在上下文窗口装不下的时候做压缩？这是 2026 年面试里问得越来越多的热点。
