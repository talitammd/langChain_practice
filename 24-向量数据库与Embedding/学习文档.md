## 一、Embedding 模型选型

### 1.1 Embedding 的本质

Embedding 模型把一段文本映射成一个固定维度的浮点数向量，语义相近的文本在向量空间中距离更近（通常用余弦相似度衡量）。

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("BAAI/bge-large-zh-v1.5")  # 中文优化模型示例
vec1 = model.encode("红烧肉怎么做")
vec2 = model.encode("红烧肉的烹饪方法")
vec3 = model.encode("今天天气怎么样")

import numpy as np
def cosine_sim(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

print(cosine_sim(vec1, vec2))  # 接近 1，语义相似
print(cosine_sim(vec1, vec3))  # 接近 0，语义无关
```

### 1.2 选型三要素

| 维度 | 说明 | 影响 |
|------|------|------|
| 语言适配 | 是否针对目标语言（如中文）专门训练/微调 | 直接决定检索准确率上限 |
| 向量维度 | 常见 384 / 768 / 1536 / 3072 维 | 维度越高表达能力越强，但存储和检索成本也越高 |
| 最大输入长度 | 模型能编码的最大 token 数 | 决定能否做整段/整篇文档级别编码 |

中文场景优先考虑专门的中文或多语言 Embedding 模型（如 BGE 系列、M3E、Qwen-Embedding 等），纯英文模型直接套用在中文语料上效果会打折扣，这是很多新手踩的坑。

### 1.3 Matryoshka Embedding（俄罗斯套娃向量，2026 新趋势）

传统 Embedding 模型训练完之后维度是固定的，想换维度只能重新训练。Matryoshka 表示学习让同一个向量的前 N 维就是一个独立可用的低维向量，可以按需截断：

```python
def truncate_embedding(full_vector: np.ndarray, target_dim: int) -> np.ndarray:
    """Matryoshka 向量支持直接截断到更低维度使用，无需重新编码"""
    truncated = full_vector[:target_dim]
    # 截断后重新归一化，保证余弦相似度计算的正确性
    return truncated / np.linalg.norm(truncated)

full_vec = model.encode("示例文本")  # 假设是 1536 维
fast_vec = truncate_embedding(full_vec, target_dim=256)  # 粗筛阶段用低维，快
precise_vec = truncate_embedding(full_vec, target_dim=1536)  # 精排阶段用全维，准
```

**工程价值**：可以用同一次编码，在检索的粗筛阶段用低维向量（快、省内存），在精排阶段用高维向量（准），不需要维护两套 Embedding 模型。

### 1.4 Query 和 Document 的非对称编码

很多 Embedding 模型区分"查询模式"和"文档模式"两种编码方式，因为用户提问和文档陈述在语言结构上分布不同：

```python
# 常见做法：用不同的指令前缀区分编码目的
def encode_query(model, text: str):
    return model.encode(f"为这个问题生成表示以检索相关文档：{text}")

def encode_document(model, text: str):
    return model.encode(f"表示这段文档以供检索：{text}")

# 反面教材：不区分模式，统一用一种方式编码
# 会导致 query 和 document 的向量分布存在系统性偏移，检索精度下降
```

这个细节是面试中"你在项目里踩过什么坑"这类问题的一个很好的加分答案。

## 二、向量数据库选型

### 2.1 核心问题：近似最近邻检索（ANN）

在百万甚至十亿级向量里找 Top-K 相似向量，暴力全量比对（brute force）不现实，需要用近似最近邻算法在速度和召回率之间取舍。最主流的索引结构是 **HNSW（Hierarchical Navigable Small World）**——一种分层图结构，检索时从顶层稀疏图快速跳转定位大致区域，再逐层下沉到底层稠密图做精细搜索。

```python
# 概念示意（真实使用中直接调用向量数据库的 API，不需要手写 HNSW）
import hnswlib

dim = 768
num_elements = 100000

index = hnswlib.Index(space='cosine', dim=dim)
index.init_index(max_elements=num_elements, ef_construction=200, M=16)

# 批量插入向量
index.add_items(document_vectors, ids=np.arange(num_elements))

# 检索时设置 ef（越大越准，越慢）
index.set_ef(50)
labels, distances = index.knn_query(query_vector, k=5)
```

`ef_construction` 和 `ef`（检索时）是 HNSW 最关键的调优参数：越大，召回率越高但延迟越高，这是面试常问的调参题。

### 2.2 三类选型方案对比

| 类型 | 代表产品 | 优点 | 适用场景 |
|------|----------|------|----------|
| 专用向量数据库 | Milvus、Weaviate、Qdrant | 性能最强、功能最全（过滤、混合检索、分片） | 数据量大（千万级以上）、检索是核心业务 |
| 传统数据库+向量插件 | PostgreSQL + pgvector | 复用现有数据库的事务和一致性能力，运维简单 | 数据量中等、已有 PostgreSQL 技术栈 |
| 云托管服务 | Pinecone、Zilliz Cloud | 免运维、快速上线 | 早期验证、中小规模、团队没有专职运维 |

**面试标准答法**：选型不是看谁"更先进"，而是看三个变量——数据规模、团队运维能力、是否需要和现有业务数据强关联做联表查询。demo 阶段用 pgvector 甚至内存向量库都可以，数据量上来、检索延迟成为瓶颈了再迁移到专用向量数据库，这是循序渐进、不过度工程化的正确路径。

### 2.3 元数据过滤（Metadata Filtering）

真实检索场景很少是纯语义检索，往往带有结构化过滤条件：

```python
# 示例：Qdrant 风格的带过滤条件检索
from qdrant_client import QdrantClient
from qdrant_client.models import Filter, FieldCondition, MatchValue

client = QdrantClient(":memory:")

# 检索时先按元数据过滤（用户ID、时间范围、文档类型），再计算向量相似度
results = client.search(
    collection_name="documents",
    query_vector=query_vector,
    query_filter=Filter(
        must=[
            FieldCondition(key="user_id", match=MatchValue(value="user_123")),
            FieldCondition(key="doc_type", match=MatchValue(value="contract")),
        ]
    ),
    limit=5,
)
```

**工程价值**：先过滤再检索，既提升了检索精度（排除了不相关用户/类型的文档），也大幅降低了向量相似度计算量，是生产系统几乎必用的优化手段。

## 三、混合检索的完整工程实现

结合第 23 节的原理，这里给出一个更完整的、贴近生产的混合检索管道：

```python
from dataclasses import dataclass


@dataclass
class RetrievalConfig:
    vector_top_k: int = 20       # 向量检索粗筛数量
    bm25_top_k: int = 20         # 关键词检索粗筛数量
    rerank_top_k: int = 5        # 重排序后最终保留数量
    relevance_threshold: float = 0.3  # 相关性阈值，低于此值拒绝回答


class ProductionRAGPipeline:
    def __init__(self, vector_store, bm25_index, reranker, config: RetrievalConfig):
        self.vector_store = vector_store
        self.bm25_index = bm25_index
        self.reranker = reranker
        self.config = config

    def retrieve(self, query: str, metadata_filter: dict | None = None) -> list[dict]:
        # 第一步：元数据过滤 + 向量检索粗筛
        vector_results = self.vector_store.search(
            query, top_k=self.config.vector_top_k, filter=metadata_filter
        )
        # 第二步：关键词检索粗筛
        bm25_results = self.bm25_index.search(query, top_k=self.config.bm25_top_k)

        # 第三步：RRF 融合去重
        merged = self._rrf_merge(vector_results, bm25_results)

        # 第四步：交叉编码器精排
        reranked = self.reranker.rerank(
            query, [doc["content"] for doc in merged], top_k=self.config.rerank_top_k
        )

        # 第五步：相关性阈值过滤（防止硬凑证据）
        return [doc for doc in reranked if doc["score"] > self.config.relevance_threshold]

    def _rrf_merge(self, list_a: list, list_b: list, k: int = 60) -> list[dict]:
        scores: dict[str, float] = {}
        docs: dict[str, dict] = {}
        for rank, doc in enumerate(list_a):
            scores[doc["id"]] = scores.get(doc["id"], 0) + 1 / (k + rank + 1)
            docs[doc["id"]] = doc
        for rank, doc in enumerate(list_b):
            scores[doc["id"]] = scores.get(doc["id"], 0) + 1 / (k + rank + 1)
            docs[doc["id"]] = doc
        sorted_ids = sorted(scores.keys(), key=lambda i: -scores[i])
        return [docs[i] for i in sorted_ids]
```

## 四、增量更新与版本管理

文档会随时间变化，向量库不能每次全量重建，需要增量更新机制：

```python
from datetime import datetime
import hashlib


class IncrementalIndexer:
    def __init__(self, vector_store, embedding_model):
        self.vector_store = vector_store
        self.embedding_model = embedding_model

    def _content_hash(self, content: str) -> str:
        """用内容哈希判断文档是否真的发生了变化，避免无意义的重新编码"""
        return hashlib.sha256(content.encode()).hexdigest()

    def upsert_document(self, doc_id: str, content: str, metadata: dict) -> None:
        new_hash = self._content_hash(content)
        existing = self.vector_store.get_by_id(doc_id)

        if existing and existing["metadata"].get("content_hash") == new_hash:
            return  # 内容没变，跳过重新编码，节省算力

        vector = self.embedding_model.encode(content)
        metadata.update({
            "content_hash": new_hash,
            "updated_at": datetime.utcnow().isoformat(),
            "version": existing["metadata"].get("version", 0) + 1 if existing else 1,
        })
        self.vector_store.upsert(doc_id, vector, content, metadata)
```

**面试考点**：为什么要做内容哈希比对？因为很多"文档更新"实际上只是元数据变了（比如权限、标签），正文没变，这种情况不应该触发重新编码，否则会造成大量不必要的 Embedding API 调用成本。

## 五、面试高频问答

**Q：向量数据库和传统数据库的索引有什么本质区别？**
A：传统数据库索引（如 B+树）解决的是"精确匹配或范围查询"，向量索引解决的是"高维空间中的近似相似度排序"，两者的数据结构和查询逻辑完全不同，向量索引普遍要在召回率和检索速度之间做近似权衡（这也是"近似"最近邻里"近似"两个字的含义）。

**Q：HNSW 的 ef 参数调大有什么代价？**
A：ef 越大，检索时遍历的候选节点越多，召回率越高，但延迟也越高。生产中通常先设一个较小值保证延迟达标，再通过评估指标（见第 27 节）验证召回率是否达标，不够再逐步调大。

**Q：什么情况下不需要向量数据库，普通数据库全文检索就够了？**
A：如果业务场景对精确关键词匹配要求高、语义泛化要求低（比如法律条文编号查询），传统全文检索（如 Elasticsearch 的倒排索引）可能比向量检索更合适，甚至可以不做语义检索。向量检索的价值在于处理"意思相近但用词不同"的查询，如果业务场景不存在这种需求，引入向量库反而是过度工程化。

### 面试模拟

7. "你的向量库存了几百万条数据，检索延迟从 50ms 涨到了 500ms，怎么排查？" 参考答法：先看是索引参数问题（ef 设置过大）还是数据规模问题（超过单机容量需要分片），再看是否可以引入元数据过滤缩小搜索范围，最后考虑是否该用 Matryoshka 低维向量做粗筛降低计算量。

8. "为什么不直接把整个知识库塞进大模型的长上下文，还需要向量检索？" 参考答法：长上下文成本随 token 数线性增长且有 lost in the middle 问题，向量检索能把海量知识库压缩到几条真正相关的证据，是成本和效果的最优平衡点，除非知识库本身很小（几千字以内）才考虑直接全量塞入。

## 七、小结

这一节把 RAG 检索层的地基讲清楚：Embedding 选型要看语言适配、维度权衡、query/document 是否区分编码；向量数据库选型要看数据规模、运维能力、是否需要和业务数据强关联；HNSW 索引和元数据过滤是生产系统检索效率的核心工程手段；增量更新机制避免了无意义的重复计算成本。
