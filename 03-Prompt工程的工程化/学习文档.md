# 第03节 · Prompt 工程的工程化

> 配套学习文档｜面试导向｜含代码示例与练习题

---

## 一、本节定位：从"会写"到"会管"

简历上写"熟悉 Prompt 工程"的人很多，但面试官真正想区分的，是你停留在"调一句话试效果"，还是已经把 Prompt 当成**软件资产**来管理。

在玩具 Demo 阶段，Prompt 就是代码里一段硬编码的字符串，改起来无所谓。但在生产环境里，一个 Agent 系统可能有几十上百个 Prompt，分散在不同链路里，被不同模型版本调用。这时候问题就来了：

- 改了一个 Prompt，怎么知道线上效果是变好还是变差？
- 模型从 GPT-4o 升级到 GPT-4.1，几十个 Prompt 全要重测吗？
- 出了线上事故，怎么快速回滚到上一个能用的 Prompt 版本？
- 一段 Prompt 同时有中英文、有变量、有 Few-shot 示例，怎么不写成一坨乱码？

**Prompt 工程的工程化**，回答的就是这四个问题。本节我们拆三件事：模板化、版本控制与可观测、Prompt 策略（Few-shot / Zero-shot / CoT）。

---

## 二、核心知识讲解

### 2.1 模板化：把 Prompt 拆成三块

新手最常见的错误，是把指令、用户输入、约束条件全揉在一个 f-string 里。这样做有两个致命问题：一是变量和指令混在一起，用户输入里只要带个花括号就可能破坏结构（甚至引发 Prompt 注入）；二是没法复用，每个场景都得重抄一遍。

工程化的做法是按职责拆三块：

| 块 | 职责 | 是否随请求变化 |
|---|---|---|
| **System（系统块）** | 定义角色、能力边界、总体约束 | 基本固定 |
| **User（用户块）** | 承载本次请求的具体输入 | 每次变化 |
| **约束块** | 输出格式、长度、语气、禁止项 | 半固定，可复用 |

拆开后，System 和约束块可以沉淀成模板库复用，User 块用模板引擎注入变量。**为什么用 Jinja2 而不是 f-string？** 因为 Jinja2 支持条件渲染（`{% if %}`）、循环（`{% for %}` 渲染 Few-shot 列表）、默认值、自动转义，这些在动态拼 Prompt 时是刚需，f-string 全做不到。

### 2.2 版本控制与可观测：Prompt 是资产，不是草稿

核心理念一句话：**Prompt 要像代码一样被版本管理**。每一版 Prompt 都该有版本号、有 commit 记录、能 diff、能回滚。生产环境常用 LangFuse、PromptLayer 这类平台来托管，关键能力有四个：

1. **版本管理**：每次改动生成新版本，线上引用版本号而非内嵌字符串。
2. **A/B 测试**：把流量切一部分给新版本，用真实指标（准确率、用户满意度、token 成本）对比，而不是凭感觉。
3. **回滚**：出问题时一键切回上一个稳定版本，不用改代码重新发布。
4. **可观测**：记录每次调用的输入、输出、延迟、token 消耗，方便事后归因。

面试高频追问：**"你怎么评估一个 Prompt 改动是好是坏？"** 标准答案不是"我看了几个 case 感觉不错"，而是"我有离线评测集（固定输入+期望输出）跑回归，线上做小流量 A/B，用量化指标决策"。

### 2.3 Prompt 策略：Zero-shot / Few-shot / CoT

这是面试必考的三个概念，要能说清区别和适用场景：

| 策略 | 做法 | 适用场景 | 代价 |
|---|---|---|---|
| **Zero-shot** | 只给指令，不给例子 | 任务简单、模型已熟悉 | 复杂任务效果不稳 |
| **Few-shot** | 给几个输入-输出示例 | 输出格式特殊、有领域风格 | 占 token、示例需精选 |
| **CoT（思维链）** | 引导模型"一步步推理" | 数学、逻辑、多步推理 | 输出变长、延迟变高 |

实战中常常组合使用：Few-shot 的示例本身就带 CoT 推理过程，既约束了格式又示范了思考方式。要注意 **Few-shot 的示例质量远比数量重要**——3 个精准示例往往胜过 10 个含噪声的示例。

## 三、代码示例

### 示例 1：Jinja2 模板化，拆三块 + 动态 Few-shot

```python
from jinja2 import Template

PROMPT_TEMPLATE = Template("""
你是一个{{ role }}，请严格遵守以下约束：
- 输出语言：{{ lang }}
- 只输出结论，不要解释过程
{% if examples %}
参考以下示例的格式：
{% for ex in examples %}
输入：{{ ex.input }}
输出：{{ ex.output }}
{% endfor %}
{% endif %}

现在请处理：
输入：{{ user_input }}
输出：
""".strip())

def build_prompt(user_input, examples=None, role="客服意图分类器", lang="中文"):
    return PROMPT_TEMPLATE.render(
        role=role,
        lang=lang,
        examples=examples or [],
        user_input=user_input,
    )

# Zero-shot 调用
print(build_prompt("我想退货"))

# Few-shot 调用：示例可以动态从样本库里挑
shots = [
    {"input": "怎么还没发货", "output": "物流查询"},
    {"input": "这个能便宜点吗", "output": "价格咨询"},
]
print(build_prompt("我想退货", examples=shots))
```

**工程要点**：示例不写死在模板里，而是作为参数传入。这样同一个模板可以在 Zero-shot 和 Few-shot 之间切换，示例也能从样本库动态检索（这其实就是 RAG 思想的雏形）。

### 示例 2：给 Prompt 加版本号 + 简单回滚

```python
from dataclasses import dataclass, field
from datetime import datetime

@dataclass
class PromptVersion:
    version: str
    content: str
    created_at: str = field(default_factory=lambda: datetime.now().isoformat())

class PromptRegistry:
    """最小化的 Prompt 版本管理器，演示生产平台的核心思想"""
    def __init__(self):
        self._store: dict[str, list[PromptVersion]] = {}

    def register(self, name: str, version: str, content: str):
        self._store.setdefault(name, []).append(
            PromptVersion(version=version, content=content)
        )

    def get(self, name: str, version: str | None = None) -> str:
        versions = self._store[name]
        if version is None:        # 默认取最新版
            return versions[-1].content
        for v in versions:
            if v.version == version:
                return v.content
        raise ValueError(f"版本 {version} 不存在")

    def rollback(self, name: str) -> str:
        """回滚：丢弃最新版，返回上一版"""
        versions = self._store[name]
        if len(versions) < 2:
            raise ValueError("没有可回滚的历史版本")
        versions.pop()
        return versions[-1].content

reg = PromptRegistry()
reg.register("intent_clf", "v1", "你是意图分类器，输出分类标签")
reg.register("intent_clf", "v2", "你是意图分类器，只输出一个中文标签，不要解释")

print(reg.get("intent_clf"))            # v2（最新）
print(reg.get("intent_clf", "v1"))      # 指定 v1
print(reg.rollback("intent_clf"))       # 回滚到 v1
```

**工程要点**：这是 LangFuse / PromptLayer 内部逻辑的简化版。生产里线上代码引用的是 `get("intent_clf", "v2")` 这样的**版本引用**，而不是内嵌字符串，回滚才不用改代码重新发布。

## 五、小结与下节预告

这节我们把 Prompt 从"一句话试效果"升级成了"可管理的软件资产"：**模板化**用 Jinja2 拆三块、动态注入示例；**版本控制与可观测**让每版 Prompt 可追溯、可 A/B、可回滚；**Prompt 策略**要分清 Zero-shot / Few-shot / CoT 的适用场景。记住贯穿全节的一句话——**改 Prompt 要靠评测集和指标说话，不靠感觉**。

但 Prompt 写得再好，模型吐回来的还是一段自由文本。Agent 要调用工具、要把结果传给下一个节点，就必须拿到**结构化、可解析、字段可靠**的输出。下一节我们讲**结构化输出与 Pydantic**——怎么让 LLM 稳定吐出合法 JSON、字段类型怎么校验、解析失败了怎么自动重试。这是从"能聊天"到"能干活"的关键一跳。

**A1.** System 定义角色与总体约束（基本固定）；User 承载本次具体输入（每次变化）；约束块管输出格式/长度/禁止项（半固定可复用）。拆开是为了**复用**（System/约束可沉淀成模板库）和**安全**（用户输入隔离，避免破坏结构或注入）。

**A3.** Zero-shot 适合简单/模型熟悉的任务，代价是复杂任务不稳；Few-shot 适合输出格式特殊或有领域风格，代价是占 token 且示例需精选；CoT 适合数学/逻辑/多步推理，代价是输出变长、延迟和成本上升。
