面试官给你一个场景："你的 Agent 同时调了五个外部 API，其中一个超时了，一个返回了 403 鉴权失败，一个被限流返回 429。你的 Agent 是直接崩掉，还是怎么处理？"这个问题考的是生产环境里 Agent 最频繁出问题的环节——工具编排与错误处理。如果你的代码里每个工具调用都没有兜底，那上线第一天就得准备值班了。

上一节我们解决了记忆怎么存怎么取。但 Agent 光有记忆还不够，它还得调工具干活。工具调用涉及外部服务，外部服务就一定会出问题——网络抖动、接口超时、限流、鉴权过期、返回脏数据。谷歌 2026 年的报告说 80% 的企业 AI 试点卡在可靠性上，大部分都卡在工具调用这个环节。

先说工具调用错误的三种类型。第一类是瞬时错误，比如网络抖动、临时超时、429 限流——这种重试几次就好了。第二类是持久错误，比如 403 鉴权失败、404 接口不存在——这种重试再多次也没用，得换方案。第三类是数据错误，接口正常返回了但内容是脏的、格式不对、或者值不合理——这种最阴险，不校验就会把错误数据传到下游。

针对这三类错误，生产级 Agent 要有四层防线。第一层是重试策略。瞬时错误要重试，但不能傻重试——要用指数退避，每次重试间隔翻倍，比如 1 秒、2 秒、4 秒。而且要设最大重试次数，一般 3 次。持久错误不重试，直接走降级。

第二层是超时控制。每个工具调用必须设超时，不能让一个慢请求卡死整个 Agent 循环。用 asyncio.wait_for 包一层，超了就抛异常走错误处理。面试官问"你的工具调用超时怎么处理"，标准答案就是 wait_for 加重试。

第三层是降级策略。工具挂了不能让整个任务崩。降级有三种方式：静默降级，工具失败了就用缓存的上次结果或者返回一个默认值；功能降级，天气接口挂了就用另一个天气 API；优雅降级，实在没替代方案就告诉用户"这个功能暂时不可用"而不是抛一个 stack trace。

第四层是熔断器模式。如果一个工具连续失败好几次，后续的调用直接短路返回失败，不再真的去调那个接口。等过一段时间再放几个请求试探一下恢复了没有。这跟电闸的原理一样——短路了就跳闸保护，防止一个挂掉的服务把整个系统拖垮。

还有一个面试高频追问：错误信息怎么给模型看？工具执行失败了，你是把原始的 stack trace 塞回给模型让它自己想办法？不行。模型看不懂 Python 的 traceback。正确做法是把错误信息翻译成自然语言——"调用天气接口失败，原因是网络超时，建议稍后重试或换用搜索功能"。让模型能理解错误并决定下一步：重试、换工具、还是直接告诉用户。

最后说一个很多人忽略的点——工具调用的幂等性。有些操作调一次和调十次效果不一样，比如转账、发邮件。如果 Agent 重试了三次，用户收到三封一样的邮件就尴尬了。所以对于非幂等操作，重试前要检查上一次是否已经执行成功了，或者在工具设计层面加幂等 token。

总结三句话。第一，工具调用错误分三类——瞬时错误重试、持久错误降级、数据错误靠校验。第二，生产级 Agent 四层防线——指数退避重试、超时控制、降级策略、熔断器模式。第三，错误信息要翻译成自然语言给模型看，非幂等操作重试前要检查上次是否成功。
