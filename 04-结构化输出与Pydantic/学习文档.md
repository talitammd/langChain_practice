# 第04节 · 结构化输出与 Pydantic

> 配套学习文档｜面试导向｜含代码示例与练习题

---

## 一、本节定位：从"能聊天"到"能干活"的关键一跳

上一节我们把 Prompt 工程化了，但模型吐回来的还是一段**自由文本**。问题在于：Agent 要调用工具、要把上一步结果传给下一个节点、要把数据写进数据库，靠的全是**字段可靠、能解析的结构化数据**，而不是散文。

自由文本有多不可靠？看几个生产环境真实翻车场景：

- 模型在 JSON 前面加了一句"好的，这是您要的结果："，`json.loads()` 当场抛异常；
- 返回的 JSON 带了 `//` 注释或尾逗号，标准解析器不认；
- 字段名拼成了 `user_name` 但你代码里要的是 `username`；
- 该返回数字的字段返回了字符串 `"25"`，下游计算炸了。

**结构化输出**就是要把这些不确定性彻底锁死。这一节的核心，是搞清楚保证结构化输出的**三层武器**，以及为什么 **Pydantic** 是把这件事做对的核心工具。

---

## 二、核心知识讲解

### 2.1 三层武器：JSON Mode / Function Calling / Structured Outputs

面试高频考点，必须能说清三者的强度差异：

| 方案 | 保证什么 | 不保证什么 | 强度 |
|---|---|---|---|
| **JSON Mode** | 输出是**合法 JSON** | 字段对不对、缺不缺、类型对不对 | 弱（只管形状） |
| **Function Calling** | 按函数签名抽取参数 | 早期模型偶有偏差 | 中 |
| **Structured Outputs** | 用 JSON Schema 在**解码层**锁死格式，字段/类型/必填全合规 | —（最强保证） | 强 |

一句话总结：**JSON Mode 管形状，Function Calling 抽参数，Structured Outputs 用 schema 锁死格式**。2025 年起 OpenAI、Claude、Gemini 都已支持原生 Structured Outputs，它是当前最该写进简历的方案。

**为什么 Structured Outputs 能"保证"合规？** 关键在 **constrained decoding（约束解码）**。模型逐 token 生成时，解码器只允许采样那些**符合 schema 语法**的 token——比如 schema 说这里该是数字，模型就采样不到字母。这是从机制上保证，而不是靠 Prompt 求模型"请一定按格式来"。

### 2.2 Pydantic：一套定义，约束 + 校验全包

手写 JSON Schema 又长又容易错。Pydantic 让你用 Python 类定义数据结构，自动转成 JSON Schema 喂给模型；模型吐回后，再用**同一个类**做解析和校验。一套定义干两件事：

1. **生成 schema**：`Model.model_json_schema()` 直接产出标准 JSON Schema。
2. **校验解析**：`Model.model_validate_json(raw)` 把模型返回的字符串解析成强类型对象，类型不符、字段缺失当场报错。

这就是为什么"Pydantic + Structured Outputs"是 2026 年的标准组合。

### 2.3 永远要有兜底：校验失败 + 带错误重试

哪怕用了 Structured Outputs，跨供应商、降级到 JSON Mode、或老模型时，仍可能解析失败。**真正拉开工程师水平的是兜底策略**：

> 校验失败 → 把 Pydantic 的报错信息**塞回给模型** → 让它"看着错误改一遍" → 重试 2~3 次 → 仍失败则走降级/告警。

`Instructor` 库就是把"Pydantic 定义 + 自动重试 + 校验"打包好的工具，生产里很省心。面试答题结构记牢：**schema 约束 → 校验 → 失败带错误信息重试**，这才是完整的三层可靠性方案。

## 三、代码示例

### 示例 1：Pydantic 定义 + OpenAI Structured Outputs

```python
from pydantic import BaseModel, Field
from openai import OpenAI

class Invoice(BaseModel):
    """发票信息抽取结果"""
    vendor: str = Field(description="开票方名称")
    amount: float = Field(description="金额，单位元", gt=0)
    date: str = Field(description="开票日期，YYYY-MM-DD")
    items: list[str] = Field(default_factory=list, description="商品明细")

client = OpenAI()

# 用 parse 接口直接拿到强类型对象，无需手动 json.loads
resp = client.beta.chat.completions.parse(
    model="gpt-4o-2024-08-06",
    messages=[
        {"role": "system", "content": "从文本中抽取发票信息"},
        {"role": "user", "content": "美团科技 2026-06-15 开票，金额 1280 元，含云服务、技术支持"},
    ],
    response_format=Invoice,   # 直接传 Pydantic 模型
)

invoice: Invoice = resp.choices[0].message.parsed
print(invoice.vendor, invoice.amount, invoice.items)
```

**工程要点**：`response_format=Invoice` 让 SDK 自动把 Pydantic 转成 JSON Schema，并在底层启用约束解码；`message.parsed` 直接是 `Invoice` 实例，类型安全，不用手动解析。

### 示例 2：手写带错误重试的兜底（不依赖框架）

```python
import json
from pydantic import BaseModel, ValidationError

class Person(BaseModel):
    name: str
    age: int

def parse_with_retry(call_llm, prompt: str, model_cls, max_retries: int = 3):
    """通用兜底：校验失败把错误塞回模型让它改"""
    last_error = None
    messages = [{"role": "user", "content": prompt}]
    for attempt in range(max_retries):
        raw = call_llm(messages)            # 调模型，返回字符串
        try:
            return model_cls.model_validate_json(raw)
        except ValidationError as e:
            last_error = e
            # 把报错喂回去，让模型"看着错误改一遍"
            messages.append({"role": "assistant", "content": raw})
            messages.append({
                "role": "user",
                "content": f"上面的输出不符合要求，校验错误如下，请仅输出修正后的合法 JSON：\n{e}",
            })
    raise RuntimeError(f"重试 {max_retries} 次仍失败: {last_error}")

# 演示用 mock：第一次返回坏数据，第二次返回正确
class MockLLM:
    def __init__(self):
        self.n = 0
    def __call__(self, messages):
        self.n += 1
        return '{"name": "张三", "age": "二十五"}' if self.n == 1 else '{"name": "张三", "age": 25}'

person = parse_with_retry(MockLLM(), "抽取姓名和年龄", Person)
print(person.age)   # 25，第二次重试成功
```

**工程要点**：核心是把 `ValidationError` 的报错文本拼回对话再请求一次。这是 Instructor 库内部逻辑的简化版，也是面试时能直接讲出来的"兜底机制"。

### 示例 3：Pydantic 字段校验器，约束业务规则

```python
from pydantic import BaseModel, field_validator

class Order(BaseModel):
    order_id: str
    status: str
    amount: float

    @field_validator("status")
    @classmethod
    def status_must_be_valid(cls, v: str) -> str:
        allowed = {"pending", "paid", "shipped", "done"}
        if v not in allowed:
            raise ValueError(f"status 必须是 {allowed} 之一，收到 {v!r}")
        return v

    @field_validator("amount")
    @classmethod
    def amount_positive(cls, v: float) -> float:
        if v <= 0:
            raise ValueError("amount 必须大于 0")
        return v

# 合法
print(Order(order_id="A1", status="paid", amount=99.0))

# 非法 status —— 会抛 ValidationError，刚好可被示例 2 的重试逻辑捕获
try:
    Order(order_id="A2", status="cancelled", amount=10)
except Exception as e:
    print("校验拦截：", e)
```

**工程要点**：Schema 不只是约束"类型"，还能用 `field_validator` 约束**业务语义**（枚举值、范围、格式）。校验越严，下游越安全，重试机制也能更早拦住坏数据。

## 五、小结与下节预告

这节我们完成了"从能聊天到能干活"的关键一跳：保证结构化输出有**三层武器**——JSON Mode 管形状、Function Calling 抽参数、Structured Outputs 用 schema 锁死格式（最硬，靠约束解码从机制上保证）；**Pydantic** 是核心工具，一套模型同时搞定 schema 生成和结果校验；最后永远要有**带错误信息重试的兜底**，别让一次格式抽风搞崩整条链路。

我们现在能让模型稳定吐出结构化数据了。但光会抽参数还不够——模型到底怎么"决定"该调哪个函数、怎么把自然语言里的信息精准填进参数？下一节我们深挖 **Function Calling / Tool Use 原理**，把这套工具调用机制从里到外拆开。这是 Agent 真正长出"手"的那一刻。

**A1.** JSON Mode 保证输出是合法 JSON，但不保证字段/类型/必填正确；Function Calling 按函数签名抽参数，保证参数结构但早期模型偶有偏差；Structured Outputs 用 JSON Schema 在解码层锁死格式，字段、类型、必填全部合规。

**A2.** 因为模型逐 token 生成时启用了约束解码：解码器只允许采样符合 schema 语法的 token（比如该是数字处采样不到字母）。这是从生成机制上保证合规，而非靠 Prompt 请求模型遵守。

**A3.** 一个 Pydantic 模型同时干两件事：①`model_json_schema()` 自动生成 JSON Schema 喂给模型做约束；②`model_validate_json()` 把模型返回解析成强类型对象并校验，类型/字段不符当场报错。

**C1.** 骨架：①优先用原生 Structured Outputs（传 Pydantic 模型），靠约束解码从机制上保证格式；②跨供应商或降级场景，用 Pydantic 做强校验；③核心是兜底——校验失败把错误信息塞回模型让它修正，重试 2~3 次；④仍失败则降级到默认值并告警，绝不让一次格式问题崩掉整条链路。可提一句"我用 Instructor 把这套封装好了"。

**C3.** 因为：①不是所有供应商/模型都支持 Structured Outputs，跨平台需要 Pydantic 做统一校验层；②Structured Outputs 保证的是"格式合规"，但**业务语义**（枚举值、数值范围、字段间约束）仍要靠 Pydantic validator 兜住；③有校验才能触发重试兜底，构成完整可靠性闭环。格式合规 ≠ 数据正确。

</details>
