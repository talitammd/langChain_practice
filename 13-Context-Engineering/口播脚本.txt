面试官问你："Prompt Engineering 和 Context Engineering 有什么区别？"如果你答不上来，说明你还停留在 2024 年的认知里。2026 年行业共识是——Prompt Engineering 关注的是你怎么问，Context Engineering 关注的是你给模型看什么。这个概念今年火到什么程度？各大框架都在围绕它重构架构，面试也成了高频题。

其实前面几节你已经在做上下文工程了——记忆压缩是上下文工程，工具错误信息翻译是上下文工程，Plan-and-Execute 的子任务上下文传递也是上下文工程。今天我们把它系统化。

先说核心定义。Context Engineering 是在运行时动态决定模型看到哪些信息、何时看到、以及如何组织这些信息。为什么这很重要？因为模型失败往往不是不懂指令，而是被喂了太多不相关信息、相互冲突的数据，或者遗漏了关键事实。上下文窗口就像模型的 RAM——容量有限，塞满了垃圾就跑不动了。

2026 年行业把上下文工程归结为四大核心操作：Write、Select、Compress、Isolate。

Write 就是把信息写到外部存储，不占上下文 token。Agent 执行过程中产生的中间结果、用户的长期偏好，写进向量数据库或者文件系统，需要的时候再取。这解决了"存"的问题。

Select 就是从外部存储里取相关信息塞进上下文。但关键是"相关"——不能把所有历史记忆全倒进去，要用检索策略筛选出跟当前任务最相关的 top-k 条。盲目塞入只会导致信息过载，模型反而表现变差。这就是 RAG 的本质——它不是独立的模块，而是上下文工程的 Select 操作。

Compress 就是把上下文里冗长的信息压缩成更短的表示。对话历史摘要、工具返回结果截断、多轮推理过程合并——上一节讲的滚动压缩就是典型应用。Anthropic 2026 年推出的 Compaction API 就是把这件事标准化了：你告诉它哪些内容可以压缩，它自动生成摘要替换原文。

Isolate 就是把上下文拆成多个隔离的窗口。复杂任务里不同子任务需要的信息不一样，全部塞一个窗口既超限又互相干扰。解决方案是每个子任务给一个独立的上下文窗口，主 Agent 只协调结果不共享细节。Multi-Agent 系统里每个 Agent 有自己的上下文，本质上就是在做 Isolate。

还有一个面试必问的问题——"Lost in the Middle"现象。研究表明，模型对上下文开头和结尾的信息关注度高，中间的信息容易被忽略。所以上下文工程里有个原则叫"重要信息放两头"：系统指令和关键约束放开头，当前问题和最近结果放结尾，填充性内容放中间。如果你把关键信息塞在 5000 token 的中间位置，模型可能根本没看到。

那上下文工程和记忆系统是什么关系？记忆系统是上下文工程的子集。记忆的写入和检索对应 Write 和 Select，记忆压缩对应 Compress，多 Agent 隔离记忆对应 Isolate。面试时先讲四大操作再落记忆系统，逻辑就非常清晰。

最后说一个工程实践中的核心概念——Token Budget 管理。上下文窗口是有限资源，你要像管预算一样管 token。比如 128K 的窗口怎么分：系统指令和工具定义占 10K，对话历史占 30K，检索到的外部知识占 20K，工具结果占 20K，给模型生成的空间留 48K。每个部分都有预算上限，超了就触发压缩或截断。面试讲出"我把上下文当预算来管"，立刻拉开段位。

总结三句话。第一，Context Engineering 关注的是给模型看什么信息——四大操作 Write 写入、Select 检索、Compress 压缩、Isolate 隔离，所有智能产品本质都是这四种操作的编排。第二，Lost in the Middle 现象要求重要信息放两头，中间塞填充内容。第三，Token Budget 管理是生产级核心技能——上下文窗口是有限资源，每个部分都有预算上限，超了就压缩。
