# 第13节：Context Engineering（上下文工程）

## 一、本节定位

2026 年最火的概念。前面几节的记忆压缩、工具错误处理、信息组织本质上都是上下文工程。本节把它系统化：**运行时怎么动态决定模型看到哪些信息、何时看到、如何组织？**

| ------------------- | ---- | --------- |
| Prompt Engineering  | 怎么问  | 写好一封邮件    |

## 三、四大核心操作

```
┌──────────────────────────────────────────┐
│          Context Engineering 四大操作      │
│                                          │
│  Write    → 存到外部，不占 token          │
│  Select   → 检索相关信息塞进上下文         │
│  Compress → 压缩冗长信息为更短表示         │
│  Isolate  → 拆成多个隔离窗口              │
└──────────────────────────────────────────┘
```

### 3.1 Write（写入）

把信息持久化到外部，不占上下文 token：

```python
# Agent 执行过程中把中间结果写到外部
def write_to_external(key: str, content: str):
    """写入外部存储，释放上下文空间"""
    # 生产中: 向量数据库 / 文件系统 / Redis
    external_store[key] = content
    # 从上下文中移除（已持久化）
    context.remove(key)
```

### 3.2 Select（检索）

从外部存储筛选相关信息塞进上下文：

```python
def select_and_inject(query: str, top_k: int = 3, max_tokens: int = 2000):
    """检索相关记忆，注入上下文"""
    # 向量相似度搜索
    results = vector_store.search(query, top_k=top_k)
    
    # Token 预算控制
    injected = []
    total_tokens = 0
    for r in results:
        if total_tokens + r.token_count > max_tokens:
            break
        injected.append(r)
        total_tokens += r.token_count
    
    return injected
```

### 3.3 Compress（压缩）

```python
def compress_context(context: str, target_ratio: float = 0.3) -> str:
    """压缩上下文，保留关键信息"""
    response = openai.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{
            "role": "user",
            "content": f"压缩以下内容，保留所有关键信息，目标长度为原文的{target_ratio*100}%:\n\n{context}"
        }],
    )
    return response.choices[0].message.content
```

### 3.4 Isolate（隔离）

```
主 Agent (全局上下文: 任务目标 + 协调信息)
    │
    ├── 子Agent A (独立上下文: 子任务A的信息)
    ├── 子Agent B (独立上下文: 子任务B的信息)
    └── 子Agent C (独立上下文: 子任务C的信息)

各子Agent 上下文互不干扰，只返回结果给主Agent
```

## 四、Lost in the Middle

### 4.1 现象

模型对上下文开头和结尾关注度高，中间信息容易被忽略。

```
注意力分布:
高 ████░░░░░░░░░░░░████ 高
   开头        中间        结尾
   
← 关注度高 → ← 关注度低 → ← 关注度高 →
```

### 4.2 应对原则

| 位置 | 放什么 | 原因 |
|------|--------|------|
| 开头 | 系统指令、关键约束、角色定义 | 模型关注度高 |
| 结尾 | 当前问题、最近结果 | 模型关注度最高 |
| 中间 | 背景信息、历史摘要 | 关注度低，放不关键的 |

## 五、Token Budget 管理

### 5.1 预算分配示例（128K 窗口）

```
总预算: 128,000 tokens
├── 系统指令 + 工具定义:  10,000 (8%)
├── 对话历史:             30,000 (23%)
├── 检索外部知识 (RAG):   20,000 (16%)
├── 工具返回结果:          20,000 (16%)
├── 生成预留空间:          48,000 (37%)
```

### 5.2 预算管理器

```python
class TokenBudgetManager:
    def __init__(self, total_budget: int = 128000):
        self.total = total_budget
        self.allocation = {
            "system": int(total_budget * 0.08),
            "history": int(total_budget * 0.23),
            "retrieval": int(total_budget * 0.16),
            "tool_results": int(total_budget * 0.16),
            "generation": int(total_budget * 0.37),
        }
        self.usage = {k: 0 for k in self.allocation}

    def can_fit(self, category: str, token_count: int) -> bool:
        return self.usage[category] + token_count <= self.allocation[category]

    def allocate(self, category: str, token_count: int) -> bool:
        if not self.can_fit(category, token_count):
            print(f"[Budget] {category} 预算不足: 已用{self.usage[category]}/{self.allocation[category]}")
            return False
        self.usage[category] += token_count
        return True

    def get_remaining(self, category: str) -> int:
        return self.allocation[category] - self.usage[category]

    def summary(self) -> str:
        lines = []
        for cat in self.allocation:
            used = self.usage[cat]
            total = self.allocation[cat]
            pct = used / total * 100
            lines.append(f"  {cat:15s}: {used:>6d}/{total:<6d} ({pct:.0f}%)")
        return "\n".join(lines)
```

## 七、面试高频题

### 题目 1：Context Engineering 和 Prompt Engineering 有什么区别？

**标准答案**：Prompt Engineering 关注"怎么问"——措辞、格式、Few-shot 示例；Context Engineering 关注"给什么看"——运行时动态决定模型看到哪些信息、何时看到、如何组织。前者是写好一封邮件，后者是管好模型的 RAM。2026 年行业认为 Context Engineering 更重要，因为模型失败更多是因为被喂了错误信息而非指令写得不好。

---

### 题目 2：上下文工程的四大操作是什么？

**标准答案**：Write（写入外部存储，释放 token）、Select（检索相关信息注入上下文）、Compress（压缩冗长信息为摘要）、Isolate（拆成多个隔离窗口，各子任务独立上下文）。所有智能产品本质都是这四种操作的编排组合。

---

### 题目 3：什么是 Lost in the Middle？怎么应对？

**标准答案**：模型对上下文开头和结尾关注度高，中间信息容易被忽略。应对原则是"重要信息放两头"：系统指令和约束放开头，当前问题和最近结果放结尾，背景信息和历史摘要放中间。如果把关键约束塞在 5000 token 的中间位置，模型可能根本没看到。

---

### 题目 4：你怎么管理上下文的 Token 预算？

**标准答案**：像管财务预算一样管 token。128K 窗口按比例分配：系统指令 8%、对话历史 23%、检索知识 16%、工具结果 16%、生成空间 37%。每个类别有预算上限，超了就触发压缩或截断。关键是生成空间必须预留充足——很多人把上下文塞满只给模型留 2K 生成，导致输出被截断。

---

### 题目 5：Multi-Agent 和上下文工程的 Isolate 操作是什么关系？

**标准答案**：Multi-Agent 本质上就是上下文工程 Isolate 操作的架构体现。每个 Agent 有独立的上下文窗口，互相不共享细节，只通过消息传递结果。这样做的好处是每个 Agent 的上下文专注、干净，不会互相干扰。主 Agent 只负责协调，不承担子任务的具体信息。
