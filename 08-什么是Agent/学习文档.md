阶段 1 我们练完了所有零件，甚至手搓了一个带工具循环的助手。但有一个根本问题需要回答——**你写的那个东西到底算不算 Agent？它和 Workflow、Chain 到底差在哪？**

## 二、核心知识讲解

### 2.1 Anthropic 的经典分法：Workflow vs Agent

Anthropic 在 2024 年底的工程博客里给出了目前行业引用最多的定义。他们把所有和大模型相关的自动化系统统称为 **Agentic Systems（智能体系统）**，然后在里面划了一刀：

| 概念 | 谁做决策 | 路径是否预定义 | 典型特征 |
|---|---|---|---|
| **Workflow** | 你的代码 | 是（预定义分支） | 路径写死，模型只在每个节点干活 |
| **Agent** | 模型自己 | 否（动态决定） | 模型决定调什么工具、走哪条路、何时停止 |

**一句话**：Workflow 里做决策的是代码；Agent 里做决策的是模型本身。

### 2.2 自治程度光谱

Chain、Workflow、Agent 不是非此即彼，而是一条**自治程度递增的光谱**：

```
纯线性          有分支/条件         模型自治
Chain ────────── Workflow ────────── Agent
 ↑                  ↑                  ↑
A→B→C           if/switch         while loop
代码写死路径     代码定义分支       模型决定路径
完全可控         高度可控           灵活但难控
```

- **Chain**：最简单的 Workflow，一条直线，A 调完调 B、B 调完调 C，没有分支没有循环。
- **Workflow**：有 if/switch 条件分支、有并行节点，但路径还是代码预定义好的。
- **Agent**：while 循环里模型自己决定下一步是什么——调工具、思考、还是停下来返回答案。

**越往右，灵活性越高，但可预测性和可控性越低。** 这是一个工程权衡，不是"越 Agent 越牛"。

### 2.3 第07节的 while 循环助手算 Agent 吗？

算。因为循环里"调不调工具、调哪个、什么时候停"是**模型在做决策**，不是代码写死的。那就符合 Agent 的定义——模型动态指导自己的流程。

但它是最简形态的 Agent。真正的生产 Agent 还需要更强的规划、记忆、反思能力——这些就是阶段 2 后面几节要学的。

### 2.4 生产里怎么选型？（面试高频）

面试官一定会问："你在生产里什么时候用 Agent、什么时候用 Workflow？"

**核心原则**：不是越 Agent 越好。

- **可预测的任务 → Workflow**：路径能穷举、需要可复现、出问题能 debug。如：ETL 管道、固定流程审批。
- **路径不可穷举 → Agent**：任务复杂到你没法预定义所有分支。如：开放域问答、自主编程、多步研究。
- **大部分生产系统 → 混合**：外层 Workflow 编排大流程，某些复杂节点里套一个 Agent 做动态决策。

这个选型原则要记牢：**能 Workflow 就 Workflow，实在不行才 Agent；最好的系统是两者混合。**

### 2.5 Agent 的四大核心能力

不管用什么定义，一个合格的 Agent 通常需要四大能力：

| 能力 | 解释 | 对应本课程哪节 |
|---|---|---|
| **感知** | 接收用户输入 + 工具返回的观察 | 第05节 Function Calling |
| **推理/规划** | 决定下一步做什么 | 第09节 ReAct / 第10节 规划 |
| **行动** | 调用工具执行操作 | 第05/07节 |
| **记忆** | 存储和检索历史信息 | 第11节 记忆系统 |

后面几节会逐一深挖。

## 三、代码示例

### 示例 1：Chain —— 纯线性，没有分支

```python
from openai import OpenAI
client = OpenAI()

def chain_example(topic: str) -> str:
    """Chain：A→B→C，代码写死路径"""
    # Step A：生成大纲
    outline = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": f"为'{topic}'写一个三点大纲"}],
    ).choices[0].message.content

    # Step B：根据大纲写摘要（路径写死：A 的输出一定流向 B）
    summary = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": f"根据以下大纲写一段摘要：\n{outline}"}],
    ).choices[0].message.content

    # Step C：翻译成英文（路径写死：B 的输出一定流向 C）
    english = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": f"翻译成英文：\n{summary}"}],
    ).choices[0].message.content

    return english

# 路径永远是 A→B→C，模型不做路径决策
```

**关键特征**：三步顺序执行，路径写死在代码里。模型只在每个节点"干活"，不决定"下一步去哪"。

### 示例 2：Workflow —— 有条件分支，但路径是代码定的

```python
def workflow_example(query: str) -> str:
    """Workflow：代码定义分支逻辑"""
    # 先让模型分类（模型干活，但分支逻辑是代码定的）
    category = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": f"判断以下问题属于哪类[天气/计算/闲聊]：{query}"}],
    ).choices[0].message.content.strip()

    # 代码定义的分支：根据分类走不同路径
    if "天气" in category:
        return handle_weather(query)      # 调天气 API
    elif "计算" in category:
        return handle_calculation(query)  # 调计算器
    else:
        return handle_chat(query)         # 纯对话

def handle_weather(q): return "天气处理..."
def handle_calculation(q): return "计算处理..."
def handle_chat(q): return "闲聊处理..."

# 分支存在，但"走哪条"是代码 if/elif 决定的
```

**关键特征**：有条件分支，但分支逻辑（if/elif）写在代码里。模型只负责分类,不决定"我要不要再调一次工具"。

### 示例 3：Agent —— 模型自己决定路径和停止

```python
import json
from openai import OpenAI

client = OpenAI()

tools = [...]       # 工具定义（省略，参见第07节）
registry = {...}    # 工具注册表

def agent_example(query: str, max_turns: int = 10) -> str:
    """Agent：模型自己决定调什么、什么时候停"""
    messages = [
        {"role": "system", "content": "你是一个助手，可以使用工具解决问题"},
        {"role": "user", "content": query},
    ]

    for _ in range(max_turns):
        resp = client.chat.completions.create(
            model="gpt-4o", messages=messages, tools=tools,
        )
        msg = resp.choices[0].message
        messages.append(msg.model_dump(exclude_none=True))

        # ★ 关键：模型自己决定"还要不要继续调工具"
        if not msg.tool_calls:
            return msg.content       # 模型自己决定停下来

        # 模型自己决定调哪个工具、传什么参数
        for call in msg.tool_calls:
            args = json.loads(call.function.arguments)
            result = registry[call.function.name](**args)
            messages.append({"role": "tool", "tool_call_id": call.id, "content": result})

    return "[达到最大轮次]"

# 模型自己做所有路径决策：调什么、几次、何时停
```

**关键特征**：while 循环里**模型做决策**——调不调工具、调哪个、什么时候停。代码只提供能力（工具列表）和安全阀（max_turns），不预定义路径。

### 示例 4：混合系统 —— 外层 Workflow 套内层 Agent

```python
def hybrid_system(task: dict) -> str:
    """生产常见模式：外层 Workflow + 内层 Agent"""
    # ━━ 外层 Workflow：代码定义大流程 ━━
    # Step 1: 验证输入（确定性逻辑，不用模型）
    if not task.get("query"):
        return "缺少查询内容"

    # Step 2: 路由（代码规则 or 简单分类）
    task_type = classify(task["query"])   # 确定性路由

    # Step 3: 复杂节点用 Agent 处理
    if task_type == "research":
        # ★ 这个节点套一个 Agent，因为研究路径不可穷举
        result = agent_example(task["query"], max_turns=8)
    elif task_type == "simple_qa":
        # 简单问题不需要 Agent，直接一次调用
        result = simple_llm_call(task["query"])
    else:
        result = "不支持的任务类型"

    # Step 4: 后处理（确定性逻辑）
    return format_output(result)

def classify(q): return "research"
def simple_llm_call(q): return "直接回答"
def format_output(r): return f"最终结果: {r}"
```

**工程要点**：这才是生产系统的真实面貌——能用确定性逻辑的地方不浪费 Agent 的灵活性，只在路径不可穷举的复杂节点让 Agent 上场。

## 五、小结与下节预告

这节我们立住了阶段 2 最根本的定义：**Agent 的本质是模型自己做路径决策**——调什么工具、走哪条路、什么时候停，由模型动态决定而非代码预定义。Chain / Workflow / Agent 是一条自治程度递增的光谱，不是越右越好，生产里按需选型，能 Workflow 就 Workflow，路径不可穷举才上 Agent，最常见的是两者混合。

定义清楚了，下一个问题就是：Agent 在循环里到底**怎么"思考"和"行动"的**？它靠什么范式来决定每一步干什么？下一节我们深挖 **ReAct 范式**——Reasoning + Acting，思考与行动交替循环。这是所有 Agent 框架的灵魂，也是面试必须能手撕的核心逻辑。
