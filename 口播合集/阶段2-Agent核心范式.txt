我见过一个候选人，简历上写着"独立设计并实现了 AI Agent 系统"，面试官说"那你给我讲讲，你的 Agent 和普通 Workflow 有什么区别？"他想了想说"Agent 就是大模型加工具调用"。面试官笑了一下没接话，紧接着连追了七个问题，从 Agent 定义一路追到自我修正，十五分钟这人就崩了。今天我把那七个追问全拆一遍，听完你就知道 Agent 核心范式到底考到什么深度。

先回到第一个问题——Agent 和 Workflow 到底差在哪。关键在决策权归谁。Anthropic 给的行业定义是：Workflow 是通过预定义代码路径编排大模型和工具的系统，走哪条路、调什么工具是你的代码写死的，模型只在每个节点干活。Agent 是模型自己动态决定下一步干什么、用什么工具、什么时候停。自治程度可以画成一条光谱：最左是 Chain，纯线性一条道走到底；中间是 Workflow，有分支有条件但路径还是代码定的；最右是 Agent，模型完全自主决策。越往右越灵活但越不可控，所以不是越 Agent 越好——可预测的任务用 Workflow 能控制能测试能复现，路径不可穷举的才上 Agent，生产里大部分系统是混合的：外层 Workflow 编排大流程，复杂节点里套一个 Agent 做动态决策。

面试官不会停。第二个追问："你的 Agent 内部到底怎么决定下一步做什么？"这就到了 ReAct 范式——所有 Agent 框架的灵魂。模型每一步走三个动作：Thought 思考当前状态、Action 选一个工具执行、Observation 看返回结果，然后循环。比如用户问北京天气，模型先 Thought 想到要调天气工具，Action 发出调用请求，Observation 拿到 32 度，再 Thought 判断可以回答了。不是一次性想好所有步骤，而是走一步看一步。它和纯 Chain-of-Thought 的区别是 CoT 只能想不能做，ReAct 边想边做边根据环境反馈修正。Function Calling 本质上就是 ReAct 的工业级结构化实现——把文本格式的 Action 变成了标准 JSON 调用，不用再靠正则解析容易出错。但 ReAct 有两个硬伤：长循环注意力漂移，跑到七八轮前面推理就开始被遗忘；还有逐步贪心，每步只看当前状态没有全局视野。

"那任务复杂了，ReAct 一路跑几十步上下文不爆吗？"第三个追问。答案是 Plan-and-Execute：先把任务拆成子任务列表再逐个执行。Planner 负责拆解，Executor 负责执行，Replanner 根据执行结果动态调整后续计划——比如搜索结果不够就临时插入一个补充调研的子任务。和 ReAct 不是替代而是互补——外层 Plan-and-Execute 管全局规划，内层 ReAct 管单步执行，就像总监定方向员工管执行。还有个省钱变体叫 ReWOO，一次性规划完不回头，大幅减少 LLM 调用次数但牺牲了灵活性，适合路径比较确定的任务。任务特别复杂就上层级规划，把子任务继续往下拆成任务树，顶层 Supervisor 做规划底层 Worker 做执行，对接 Multi-Agent 系统。

面试官继续追："对话三十轮了，用户提到第一轮说的事，你的 Agent 还记得吗？"很多人答把历史全塞 prompt 里，面试官追一句上下文只有 128K 塞得下吗就卡住了。第四个问题考记忆系统。短期记忆就是上下文窗口，快但容量有限。装不下就做滚动压缩——保留最近几轮原文因为信息密度最高，把更早的摘要成短文本替换掉。长期记忆存外部，写入和检索跟 RAG 一个思路，只不过检索的是 Agent 自己的历史经验。2026 前沿把记忆分成工作、情景、语义、程序四层，面试说出这四层立刻拉开段位。生产里还要防记忆腐蚀——只往里加不清理，检索噪声越来越大，有用记忆被过时信息淹没，要设过期时间做定期清理。

"你 Agent 调了十几个工具，其中一个超时了怎么办？"第五个追问，考工具编排。错误分三种：瞬时错误比如网络抖动用指数退避重试，每次间隔翻倍最多三次；持久错误比如鉴权失败重试也没用，直接降级——搜索引擎挂了换缓存数据，实在没替代就告诉用户功能不可用而不是甩一个 stack trace；数据错误最阴险，接口返回了但内容是脏的，不校验就传到下游。连续失败触发熔断器，后续调用直接短路不再打挂掉的服务。工具返回的技术报错要翻译成自然语言给模型看——"调用失败原因是网络超时建议换用搜索功能"，不然模型看不懂 traceback 不知道下一步该怎么办。还有个容易被忽略的——幂等性，重试时同一个扣款操作不能执行两次，非幂等操作重试前必须检查上次是否已成功。

"上下文窗口是有限的，你怎么管？"第六个追问，2026 年最火的 Context Engineering。Prompt Engineering 关注怎么问，Context Engineering 关注给模型看什么——运行时动态决定模型看到哪些信息、何时看到、如何组织。四大操作：Write 把中间结果存外部不占 token，Select 检索相关信息塞进来，Compress 把冗长文本压成摘要，Isolate 给每个子任务独立上下文窗口互不干扰。前面几节讲的记忆压缩、工具错误翻译、子任务隔离本质上都是这四种操作的编排。还有 Lost in the Middle 现象——模型对开头和结尾关注度高，中间容易被忽略，重要信息放两头。Token 要当预算管，128K 窗口按比例分给系统指令、历史、检索知识、工具结果和生成空间，超了就压缩，不能把上下文塞满只给模型留 2K 生成空间导致输出被截断。

最后一个追问："Agent 生成的代码报错了，它能自己改吗？"这考反思与自我修正。最基础的 Reflection 让模型审查自己的输出，但纯自评有确认偏差，模型倾向于觉得自己没问题。Reflexion 加了两样东西：口头反思——不只说有错而是具体写出错在哪、为什么错、下次怎么办；情景记忆——把反思结论存下来，下一轮重试时塞进 prompt 不犯同样的错。Self-Refine 是输出提交前反复打磨，生成、批评、修改循环到满意，不需要外部信号。还有 CRITIC 范式，用外部工具验证——代码跑一下看报不报错，比纯自评靠谱得多。但自我修正不是万能药——2024 年研究表明没有外部反馈信号时模型可能越改越差，因为模型连正确答案都认不出来。工程实践优先用工具验证而不是模型自评，同时设最大重试次数避免死循环。

七个追问全拆完了。面试官从头到尾沿着"Agent 定义 → ReAct → 规划 → 记忆 → 工具编排 → 上下文工程 → 反思修正"这条链路，一步步验证你是真懂 Agent 核心范式还是只会调框架 API。这七块就是 Agent 工程师的中枢骨架，后面所有框架和协议都是在这个基础上做工程封装。下一期我们直接上手实战，把这七块全拼进一个能跑的 Agent 里。关注我，下期见。
