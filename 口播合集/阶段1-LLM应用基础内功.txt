我见过一个三年经验的后端开发，面试 Agent 岗位，前两分钟项目经历聊得还挺顺，结果面试官突然问了一句"大模型为什么会产生幻觉"，他想了想说"训练数据有噪声"。面试官笑了一下没接话，紧接着追了一句"那你把温度调到零幻觉是不是就没了？"他彻底卡住了。然后面试官连着追了四个问题，每个都答不到点上，十五分钟提前结束。今天我把那四个追问全给你拆一遍，听完你就知道 Agent 岗位的原理层到底考到什么深度。

先回到第一个问题——大模型为什么会幻觉。要答好这个，你得先搞清楚它到底在干什么。说穿了它一辈子只做一件事：根据上文预测下一个最可能的 token。不是在"理解"你的问题，而是在玩一个巨型文字接龙——算出下一个 token 的概率分布，挑一个接上去，再把接上去的当新上文，继续预测下一个。token 就是模型眼里的最小文字单位，一个英文词、半个中文字都可能是一个 token，模型不认字，只认这些被编号的碎片。那为什么接龙还会接错？因为它挑字不是只挑概率最高那个，而是按概率分布去采样。这里有两个面试必问的旋钮：Temperature 温度，越高分布越平、越随机越有创造力，越低越确定越保守；Top-p，只在累计概率达到 p 的那一小撮候选里挑，过滤掉长尾的胡话。这俩就是你控制模型放飞还是稳重的方向盘。那温度调到零呢？还是会幻觉。OpenAI 2025 年底从数学上证明了：幻觉是 next-token prediction 的统计必然，模型被"不会也要蒙、蒙对了有分"的训练评估方式给教坏了。所以幻觉压不到零，你能做的是控制它、检测它、用工具兜底——答到这一层，第一个问题才算过关。另外还有个硬约束你必须知道：上下文窗口，模型一次能看的 token 有上限，超了前面的就被截断遗忘，后面所有记忆系统和 RAG 的根子都在这。

面试官不会停的。他合上电脑看着你："你说 Prompt 工程很重要，那我们线上跑着几十个 Prompt，模型一升级全崩了，你怎么管？"这个问题专门筛掉那些只会在对话框里反复试、试满意了复制粘贴到代码里的人。生产里 Prompt 是要版本管理的工程资产。第一步你得模板化——用 Jinja2 把 Prompt 拆成系统指令、用户输入、输出约束三块，变量用占位符填进去，改规则只改一处不用满项目搜。第二步版本控制——像管代码一样给每个 Prompt 打版本号，上线前 A/B 测试拿数据对比，出问题一键回滚，LangFuse 就干这个，没有版本和回滚等于生产裸奔。第三步你得会用技巧提质——Few-shot 给标准示例让模型照猫画虎，Chain-of-Thought 让模型先推理再答、复杂任务准确率明显提升。但注意 Prompt 不是越长越好，token 爆了中间信息反而被模型忽略，精准比冗长重要得多。

你以为答完了，面试官又来了："好，那模型返回的 JSON 偶尔开头带一句废话，你的 json.loads 当场炸了，线上怎么兜底？"这就到了结构化输出。你得清楚三层武器从弱到强：JSON Mode 只保证返回合法 JSON 但管不了字段对不对，只约束了形状没约束内容；Function Calling 按函数签名抽参数，本质也是结构化输出；最硬的一层叫 Structured Outputs——直接用 JSON Schema 在解码层面锁死格式，字段、类型、必填项一个都不会错。定义 Schema 用 Pydantic，Python 写个模型自动转成 JSON Schema 喂给 API，返回后同一个模型校验解析，类型不对当场报错，一套定义约束加校验全包。万一校验还是过不了？成熟做法是带重试的兜底：把校验报错信息塞回给模型让它改，重试两三次，Instructor 库就是干这个的。面试答题结构记住：schema 约束 → 校验 → 失败带错误信息重试，三步才是完整可靠性方案。

面试官继续追深："你说模型能调函数，那它真的执行了那个函数吗？"很多人这里翻车——脱口而出"模型调了天气接口"。错了。模型自己从来不执行任何函数，它只输出一个结构化的调用请求，告诉你"我想调 get_weather，参数是北京"。真正执行函数查接口跑代码的，是你的应用程序。模型只动嘴，干活的是你的代码。完整流程是三轮对话：第一轮你把工具定义加用户问题发给模型；第二轮模型不直接回答，返回 tool_calls 包含函数名和抽取的参数；第三轮你执行完函数把结果回填，模型才给最终答复。发问、抽参、回填，三轮闭环。高频考点——并行工具调用：用户一句话查三个城市天气，模型一轮返回多个 tool_calls，你并发执行再一起回填，省掉多轮往返直接压延迟。参数合法性靠 strict mode 开启后 schema 死死约束。安全层面，模型输出的参数本质上是不可信的外部输入——它让你删文件转账你能闭眼执行吗？参数校验、权限控制、危险操作加人工确认，把模型输出当用户输入来防。

到这面试已经快二十分钟了，面试官最后甩一个工程体验题："你的 Agent 调了模型，用户干等五秒才看到一大坨文字糊脸上，怎么优化？"答案是流式输出——让模型边生成边往前端推 token，用户看到文字一个个蹦出来，首字延迟从几秒压到几百毫秒，体验直接质变。底层靠 SSE，Server-Sent Events，基于 HTTP 长连接单向推送，生成一个 token 就推一个数据块过来。为什么不用 WebSocket？因为大模型输出是典型的单向数据流，SSE 就够了，比 WebSocket 轻量，浏览器原生支持 EventSource 接口开箱即用。面试记住这句：单向流选 SSE，双向交互才上 WebSocket。但流式只解决了体验问题，真正拉开工程差距的是异步编程。大模型 API 是 IO 密集型调用，发出请求后大部分时间在等网络回来，同步代码一等线程就卡死了。async/await 在等 IO 时让出控制权给事件循环，同一线程并发扛几十上百个请求，Agent 里并行工具调用底层就是 asyncio.gather 并发等多个 IO 完成。生产里三个坑必须提前知道：Semaphore 限流防并发太猛被 API 429、wait_for 超时防一个慢请求卡死整个循环、try/except 错误隔离防一个异常炸掉所有并发任务。面试讲出这三点，面试官就知道你真写过生产级的异步代码而不是只跑过 demo。

五个追问全拆完了。回头看，面试官从头到尾只在做一件事：沿着"大模型原理 → Prompt 管理 → 结构化输出 → 工具调用 → 流式异步"这条链路，一步步验证你到底是只会调 API 还是真懂底层。这五块就是 Agent 工程师的地基，地基不牢后面的框架和架构全是空中楼阁。下一期我们直接上手实战，把这五块全拼在一起，手写一个不依赖任何框架的极简助手——做完你就有了一个能写进简历、面试时能从头讲到尾的完整项目。关注我，下期见。
