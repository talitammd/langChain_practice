面试官问你"给 Agent 接一个知识库需要几步"，你说"很简单，把文档切块存进向量库，用户提问的时候检索出来塞进 prompt 就行了"。面试官笑了笑，追问一句"如果用户问的问题需要综合三份文档才能回答，你的检索只返回了最相关的那一份呢？"你答不上来了——这就是今天要讲的，RAG 远不是"塞进 prompt"这么简单。

先说 RAG 是什么、为什么需要它。大模型的知识被训练数据的截止时间锁死，也不知道你公司内部的私有文档、你上周写的代码、你们产品的最新价格表。两条路解决这个问题：一条是微调，把新知识揉进模型参数里，成本高、更新慢、还有灾难性遗忘的风险；另一条是 RAG，检索增强生成——把相关文档在推理时实时检索出来，作为上下文喂给模型，模型基于这些真实资料生成回答。2026 年生产系统几乎清一色选 RAG，因为它成本低、更新快、而且答案可以溯源，用户可以点开看"这句话是从哪份文档来的"，这在企业场景是刚需。

那"陷阱"到底在哪？我们把一个 RAG 系统拆成三个环节来看：切块、检索、生成。每个环节都有一个新手必踩的坑。

切块环节的坑叫"一刀切"。很多人直接按固定字符数切文档，比如每 500 字一块，这样切出来的块经常在句子中间断开，一个完整的因果关系被切成两半，检索到其中一半，语义就是残缺的。生产做法是语义切块——按段落、按标题层级切，保证每一块本身语义完整，2026 年更进阶的做法叫 late chunking，先把整篇文档编码出上下文感知的向量，再切块，这样即使切开了，每块的向量依然带着全文的语境信息，不会因为切错位置而语义失真。

检索环节的坑叫"唯余弦相似度论"。纯向量检索本质上是语义相似度匹配，但用户问题里如果包含精确的专有名词、订单号、产品型号这类信息，向量检索经常找不准——因为"语义相似"不等于"包含这个词"。解决方案是混合检索，把传统的关键词检索 BM25 和向量检索结合起来，各自发挥所长，融合排序用倒数排名融合 RRF 算法。2026 年几乎所有生产级 RAG 都是混合检索起步，纯向量检索已经被认为是"新手方案"。

检索环节还有第二个坑——检索到的候选文档不一定是最相关的那几个，向量检索召回的是"大致靠谱"的一批，真正精确排序需要一个专门的重排序模型，用交叉编码器把用户问题和每个候选文档一起编码打分，这一步叫 reranking，能显著提升最终塞进 prompt 的文档质量，是 2026 年 RAG pipeline 里被反复验证性价比最高的一环。

生成环节的坑叫"垃圾进垃圾出"。就算检索检得再准，如果模型拿到一堆不相关的上下文照样会瞎编，甚至会被无关信息干扰产生新的幻觉。这里有个反直觉的现象——检索到的文档数量不是越多越好，塞太多不相关信息反而会稀释模型的注意力，让它找不到真正有用的那一句话，这个现象叫"lost in the middle"，长上下文中间的信息容易被模型忽略。所以生产系统会做二次过滤，检索、重排、再精选，最后只把三五条真正相关的证据喂给模型。

回到开头那个面试官的追问——多跳问题检索不全怎么办？这正是本节最后要点透的核心陷阱：朴素 RAG 只做"一次检索、一次生成"，遇到需要综合多份文档才能回答的问题就会露馅。2026 年的解法是 agentic RAG，让模型自己判断"这一轮检索到的信息够不够回答问题"，不够就重新生成检索词再查一轮，这本质上是把 RAG 也套进了 ReAct 循环里，检索本身变成了一个可以被规划、被反思的动作，而不是流程里死板的一步。

面试标准答法：RAG 不是"检索加生成"两步走的简单管道，而是一套需要在切块、检索、生成三层分别做工程优化的系统，混合检索、重排序、agentic 多跳检索这三件事，是从玩具项目到生产级 RAG 系统的分水岭。下一节我们具体拆开向量数据库和 Embedding 这一层，讲清楚分块策略到底怎么选、混合检索的代码怎么写。

上节课讲完 RAG 的三大陷阱，面试官接着追问："你说要做混合检索，那向量数据库你会怎么选？Embedding 模型呢？"很多人这时候只会说"我用的 Pinecone"或者"我用的 OpenAI 的 embedding"，再往下问选型依据、维度怎么定、索引怎么建，就卡住了。这节课把向量数据库和 Embedding 这一层的选型逻辑讲透。

先说 Embedding 模型怎么选。Embedding 本质是把文本映射成一个高维向量，语义相近的文本在向量空间里距离也相近。选型看三个维度：第一是语言能力，中文场景一定要选对中文优化过的模型，纯英文模型在中文上的检索效果会明显打折扣；第二是维度大小，维度越高表达能力越强，但存储成本和检索延迟也越高，1536 维和 3072 维之间要根据数据规模和延迟要求权衡；第三是上下文长度，如果你要做 late chunking 或者对长文档整体编码，模型能接受的最大 token 数很关键。2026 年一个新趋势是 Matryoshka Embedding，俄罗斯套娃式的向量表示，同一个模型输出的向量可以被截断到不同维度使用而不用重新训练，方便你在检索速度和精度之间动态取舍。

选完模型还有一个常被忽略的细节——一定要问自己"文档和用户问题是不是应该用不同的方式编码"。很多 Embedding 模型区分 query 和 document 两种编码模式，因为用户提问通常是疑问句、比较简短，而文档是陈述句、篇幅更长，用同一套编码方式硬套，两者在向量空间里的分布特性其实不完全对齐，用对应的模式编码能明显提升检索准确率，这是一个面试里问"你踩过什么坑"的好答案。

接下来说向量数据库。向量数据库要解决的核心问题是，在几百万甚至几十亿条向量里，怎么快速找到和查询向量最相似的那几个，不可能对每条向量做暴力全量比对，这就要用到近似最近邻索引，最常见的是 HNSW，一种分层的图结构索引，在检索速度和召回率之间做了很好的平衡，几乎是现在所有主流向量数据库的默认索引方式。

选型上，2026 年的格局大致分三类。第一类是专用向量数据库，比如 Milvus、Weaviate、Qdrant，专门为大规模向量检索设计，性能最强、功能最全，适合数据量特别大、检索是核心业务的场景。第二类是传统数据库加向量插件，比如 PostgreSQL 加 pgvector，优点是不用额外维护一套新的存储系统，数据一致性和事务能力都是现成的，适合数据量中等、团队不想增加运维复杂度的场景。第三类是云厂商托管服务，比如 Pinecone，优点是免运维、开箱即用，适合快速验证和中小规模项目。面试官问怎么选，你回答的核心逻辑应该是——先看数据规模和团队运维能力，再看是否需要和现有业务数据强关联，而不是无脑追新。

选完存储还要考虑一个容易被忽视的工程细节：元数据过滤。真实场景里检索经常不是纯语义检索，而是"在某个用户的文档里找""在某个时间范围内找"，向量数据库都支持给每条向量附加元数据，检索时先按元数据过滤缩小范围，再做向量相似度计算，这既提升了检索精度，也大幅降低了计算量，是生产系统里几乎必用的技巧。

最后说说更新和维护。文档会变，向量库也要跟着更新，如果每次都全量重新编码重新入库，成本很高。生产系统一般用增量更新策略，只对变更的文档重新切块、编码、替换旧向量，同时给每条向量打上版本号或时间戳，方便追溯和回滚。

面试标准答法是这样：向量数据库选型要看数据规模、运维成本、是否需要和业务数据强关联三个维度，Embedding 模型选型要看语言适配、维度和延迟的权衡、query 和 document 是否需要区分编码，这些工程细节恰恰是从"能跑通 demo"到"扛得住生产"的分水岭。下一节我们往前一步，看看当问题涉及实体关系、需要多跳推理的时候，向量检索的天花板在哪，GraphRAG 怎么补上这块短板。

面试官给你出一道题："知识库里有一千份企业投资公告，用户问'哪些人同时投资过 A 公司和 B 公司'，你的 RAG 系统怎么回答？"你如果还是老老实实向量检索一遍塞给模型，大概率会翻车——因为这个问题的答案不在任何一份单独的文档里，而是散落在多份文档中的实体关系里，需要把"张三投了A"和"张三投了B"这两条信息在头脑里拼起来才能得出结论。这正是向量检索的天花板，也是 GraphRAG 要解决的问题。

先搞清楚为什么向量检索在这类问题上会失灵。向量检索的本质是语义相似度匹配，它擅长回答"和这段话意思相近的内容在哪"，但它不擅长做"关系推理"，因为向量空间里没有显式的"谁投资了谁"这种结构化关系，只有模糊的语义距离。当答案需要跨越多个文档、把多条独立信息按关系串联起来的时候，向量检索一次调用只能捞到"看起来最相关"的那一批文档，答案所需的另一半信息可能因为语义上不够"像"而被漏掉，这类问题叫多跳推理问题。

GraphRAG 的思路是反过来的。它不再把文档全部打散成向量堆在一起，而是先让大模型阅读所有文档，抽取出里面的实体和关系，构建成一张知识图谱——节点是实体，比如人名、公司名，边是关系，比如投资了、任职于、收购了。构建完这张图之后，回答问题不再是单纯做向量相似度检索，而是可以在图上做遍历——从"张三"这个节点出发，沿着"投资了"这条边，一步步走到"A 公司""B 公司"，这种图遍历天然支持多跳查询，因为关系已经被显式地结构化存储下来了，不需要模型自己去脑补。

微软 2024 年发布的 GraphRAG 是这个方向的标杆实现，它的核心流程分几步：先把文档切块，用大模型对每一块抽取实体和关系三元组，然后把所有块抽取出来的实体做去重合并，构建成一张完整的图，接着在图上做社区检测，把关系紧密的实体聚类成一个个"社区"，再让大模型给每个社区生成一份摘要。查询的时候有两种模式，局部查询是从具体实体出发做图遍历，回答关于个别实体的具体问题；全局查询是直接在社区摘要上检索，回答"整个数据集里的主要趋势是什么"这种需要俯瞰全局的问题，这是向量检索完全做不到的能力。

不过 GraphRAG 有个绕不开的代价——构建这张图非常贵。每一块文档都要过一次大模型做实体关系抽取，文档量一大，构建成本和时间会线性甚至超线性增长，而且图谱质量高度依赖抽取的准确率，实体消歧没做好，"张三"和"张先生"被识别成两个不同节点，图就是错的。所以 2026 年的工程共识是不要无脑上 GraphRAG，而是先问自己一个问题：业务里有没有大量需要多跳关系推理的查询，如果有，图的构建成本能不能被摊薄到长期使用中，值不值得。

现实中更常见的做法是混合架构，而不是非黑即白地选边站。大部分查询走向量检索加重排序就够了，只有识别出用户问题涉及关系推理的时候，才路由到图查询这条路径，两条路径的结果可以合并后再喂给大模型。这个路由判断本身可以交给一个轻量的分类器或者用大模型做一次意图识别，判断这个问题更适合语义检索还是图遍历。

面试官问到这里，标准答法是这样：GraphRAG 不是向量 RAG 的替代品，而是针对多跳关系推理这个特定短板的补丁，选型依据是业务里有没有真实存在的关系型查询需求，工程上通常做成向量检索和图查询并存的混合架构，用一个路由层决定走哪条路径，而不是所有查询都走最贵的那条路。这就是这一阶段关于检索技术的全部内容，从切块、混合检索、重排序，到多跳推理和知识图谱，下一节我们要把这些技术全部整合到一个真实项目里，搭一个可以追溯信息来源的企业知识库 Agent。

前三节课讲了 RAG 的原理陷阱、向量数据库和 Embedding 选型、GraphRAG 多跳检索——全是分散的知识点。面试官不会满足于你把每个概念都说清楚，他要看的是你能不能把这些拼成一个完整、能打的系统。这节课我们就把阶段 4 的所有技术整合到一个项目里：一个可以追溯信息来源的企业知识库 Agent。

先说这个项目要解决什么问题。企业内部有大量分散的文档——制度文件、产品手册、历史项目复盘，员工问问题，普通聊天机器人要么答不上来要么一本正经地胡说八道。这个项目的目标是让 Agent 基于真实文档回答问题，而且每句话都能标注出处，用户可以点开验证，这是企业场景里能不能真正上生产的分水岭，也是这一整套 RAG 技术最有说服力的落地场景。

架构上分四层。第一层是索引构建层，文档先经过语义切块，再用 Embedding 模型编码存入向量库，同时对文档做实体关系抽取，构建一张轻量知识图谱，向量索引和图谱索引并行存在，谁也不替代谁。第二层是查询路由层，来了一个问题先判断它是普通语义查询还是关系推理查询，普通问题走向量检索加混合检索加重排序这条经典管道，涉及"谁和谁有关系""哪些实体符合某个条件"这类问题走图查询。第三层是生成层，不管走哪条检索路径，最终都要把证据和来源信息一起交给大模型，让它在生成回答的同时标注每句话引用了第几号证据。第四层是溯源层，把生成结果和原始证据做映射，前端可以展示"这句话来自于哪份文档的哪一段"，用户点开就能看原文核实。

代码实现上有几个关键设计点值得强调。混合检索用 RRF 融合关键词检索和向量检索的结果，粗筛召回二十条，交给交叉编码器重排序精选出五条，这是上节课讲的性价比最高的组合。检索到结果之后不是直接塞给模型，而是先做相关性阈值过滤，分数太低的证据直接丢弃，宁可诚实地说"知识库里没有相关信息"，也不能让模型硬凑答案。生成的时候用结构化输出强制模型给每个论断标注引用编号，这样溯源信息不是靠正则匹配硬解析出来的，而是模型输出结构里自带的字段，稳定性高很多。

路由层的设计也值得展开讲。判断一个问题是走向量检索还是图查询，本质上是一次轻量的意图分类，可以用一次小模型调用完成，也可以用规则引擎做初步筛选再交给模型确认，两条路径的结果甚至可以同时跑、同时展示，取决于对延迟的容忍度。

这个项目串起来的知识点非常密集：语义切块和混合检索来自第 23 节，向量数据库选型和 Embedding 编码来自第 24 节，知识图谱构建和路由判断来自第 25 节，而结构化输出溯源和相关性阈值兜底则是把阶段 1 学的结构化输出技术用在了新的场景里。面试的时候讲这个项目，可以从"为什么不是简单的向量检索"这个问题切入，一路讲到路由设计和溯源机制，每一层都有技术决策可以展开，是一个信息密度很高的项目素材。

到这里阶段 4 的四节课全部结束，从 RAG 原理到向量数据库到 GraphRAG 再到项目整合，你已经具备了给 Agent 接上一个真正可用知识库的完整能力。下一阶段我们进入生产化和求职冲刺——怎么科学证明你的 Agent 变好了，怎么在生产环境里追踪它的一举一动，怎么把成本和延迟压下来，最后怎么把这些项目包装成拿到 offer 的面试武器。
