面试官问你："你的 Agent 生成了一个 SQL 查询，执行报错了，它会自己改吗？"很多人答"会啊，我把报错信息丢回给模型让它重新生成"。面试官追一句"那它改了三次还是错怎么办？你有没有遇到过越改越离谱的情况？"这就考你懂不懂 Agent 的反思与自我修正。

前面几节我们讲的都是"生成一次就完"的模式——ReAct 做完一轮就进下一轮，Plan-and-Execute 执行完就收工。但真实场景里，Agent 第一版输出往往有问题：SQL 语法错了，代码有 bug，推理链断了。如果 Agent 能自己发现错误、自己修正，整个系统的可靠性就能上一个台阶。

最基础的形式叫 Reflection。就是让 Agent 在输出之后加一步自我审查——"我刚才的回答有没有问题？"用 LLM 自己当评审员，检查自己的输出。听起来简单，但有个关键陷阱：研究表明模型审查自己的输出时存在"自我确认偏差"，倾向于觉得自己的答案没问题。所以纯自我审查的改进幅度有限。

2023 年 Shinn 团队提出了 Reflexion，这是目前面试最常考的范式。它在自我审查基础上加了两个东西：第一个是"口头反思"——不只是说"有错"，而是具体写出"我哪里错了、为什么错、下次应该怎么做"。第二个是"情景记忆"——把这次反思的结论存下来，下一轮尝试时把它放进上下文，让模型不犯同样的错。这就像人做完题对答案，不光打个叉，而是写出"我错在哪了"，下次考试前翻出来看一遍。

Reflexion 的完整流程是：生成→评估→反思→重试。评估可以用外部工具，比如跑测试用例、执行代码看结果；也可以用另一个 LLM 当裁判。反思环节产出一段自然语言的"经验教训"，存进记忆。重试时把这段经验教训塞进 prompt，模型就带着上次的教训重新生成。

再说说 Self-Refine。它跟 Reflexion 的区别是：Reflexion 是"执行错了再反思"，Self-Refine 是"输出还没提交就开始打磨"。流程是生成→批评→修改→再批评→再修改，循环到满意为止。适合写文案、改代码这种需要多轮打磨的场景。关键是要给模型一个明确的"停止条件"——比如批评环节输出"无需修改"就停，否则会无限循环烧 token。

还有一个进阶范式叫 CRITIC。它的核心思想是自我修正不能只靠自己，得用外部工具验证。比如你生成了一个事实陈述，用搜索引擎验证对不对；生成了代码，跑一下看报不报错；生成了数学推导，用计算器验证中间步骤。CRITIC = 自我批评 + 外部工具验证，比纯自我审查靠谱得多。

但面试官最爱追的一个问题是："自我修正一定有效吗？"答案是：不一定。2024 年的重要研究发现，在模型能力较弱的场景下，自我修正反而会降低性能——因为模型连正确答案都认不出来，越改越差。自我修正有效的前提是：要么有外部反馈信号（测试通过、工具验证），要么模型在"审查"任务上的能力强于"生成"任务。所以工程实践中的最佳实践是：用外部工具做评估，而不是让模型自己评自己。

总结三句话。第一，Reflection 是让 Agent 自我审查，但纯自我审查有确认偏差，改进有限。第二，Reflexion 加了口头反思和情景记忆，把"错在哪了"写下来存起来，下次不犯同样的错——这是面试最常考的范式。第三，自我修正不是万能药，没有外部反馈信号时可能越改越差，工程实践优先用工具验证而不是模型自评。
