先问你一个用户体验上的生死问题：你的 Agent 调了模型，五秒后一大坨文字啪地糊用户脸上——请问用户的体验是什么？不是"哇好快"，而是"卡了吧"。ChatGPT 为什么让你觉得它在"思考着打字"？因为它用了流式输出。今天这一节，我们就把流式输出和背后的异步编程搞透。

上一节我们给 Agent 装上了手——Function Calling。但如果每次调用都要等模型把几百上千个 token 全部生成完才返回，用户在前端就只能干等一个白屏或者转圈圈。流式输出就是打破这种"全生成完再返回"的等待的。它让模型边生成边往前端推 token，用户看到文字一个个蹦出来,首字延迟从几秒压到几百毫秒,体验直接质变。

那它底层是怎么实现的？答案就是三个字母——SSE，Server-Sent Events，服务端推送事件。它基于 HTTP 长连接，服务端生成一个 token 就推一个数据块过来，直到推完发一个结束标记。你可能会想,为什么不用 WebSocket？因为大模型流式输出是典型的单向数据流，服务端推、客户端收。SSE 就够了，比 WebSocket 轻量很多，不用维护双向连接，浏览器原生支持 EventSource 接口，开箱即用。面试官问你 SSE 和 WebSocket 怎么选，记住这句——单向流选 SSE，双向交互才上 WebSocket。

讲到这有一个问题就避不开了：大模型 API 是典型的 IO 密集型调用，你请求出去之后，大部分时间在等网络回来。如果你用同步代码，一个请求等着，整个线程就卡住了。这时候 async/await 的价值就出来了——在等 IO 的时候让出控制权，让事件循环去处理别的请求，一个线程就能并发扛住几十上百个请求。这在 Agent 里尤其重要——上一节讲的并行工具调用，底层就是靠 asyncio.gather 并发等多个 IO 的。

但异步编程有几个生产里一定会踩的坑,你得提前知道。第一个是限流,你并发太猛 API 直接给你 429 限速,所以要用 Semaphore 控制同时发出的请求数。第二个是超时,一个慢请求卡住了别让它卡死整个循环,asyncio.wait_for 加个超时就行。第三个是错误隔离,一个请求抛异常不能影响其他并发任务,要用 try/except 包好每个协程。记住这三个坑：限流、超时、错误隔离——面试里讲出这三点,就说明你真写过异步的生产代码。

然后还有一个工程细节值得聊一句：流式输出里如果模型中途触发了工具调用怎么办？这时候你在 stream 里会收到带 tool_calls 的 chunk，你得攒起来拼完整的调用请求,执行完工具,再把结果回填继续 stream 后续文本。这个流式加工具调用的合并处理,是实际写代码时绕不开的。

所以这一节你带走三句话。第一,流式输出用 SSE 实现,边生成边推,把首字延迟压到几百毫秒,用户体验质变——单向流选 SSE,双向才需要 WebSocket。第二,大模型 API 是 IO 密集型,async/await 让等 IO 时让出控制权,一个线程并发扛大量请求。第三,异步生产三件套——Semaphore 限流、wait_for 超时、try/except 错误隔离,这三个不做,线上一定翻车。

到这里，阶段 1 的内功篇就差最后一步了。下一节是阶段 1 的项目实战——我们把前面学的 Prompt 模板化、结构化输出、工具调用、流式响应全拼在一起,手写一个不依赖任何框架的极简助手。做完这个,你就有了一个能写进简历的从零手搓的项目,然后我们正式进入阶段 2,去啃 Agent 的核心范式。
