# 第23节：RAG 原理与陷阱 — 检索增强为什么不是"塞进 prompt"那么简单

## 一、为什么需要 RAG

大模型有三个天然局限：知识有截止日期、不知道企业私有数据、上下文窗口再大也装不下全部知识库。解决办法有两条路：

| 方案 | 优点 | 缺点 |
|------|------|------|
| 微调（Fine-tuning） | 知识内化到参数里，推理时无需额外检索 | 成本高、更新慢、有灾难性遗忘风险、无法溯源 |
| RAG（检索增强生成） | 成本低、更新快（改文档不用重训模型）、答案可溯源 | 检索质量直接决定回答质量，工程复杂度在检索侧 |

2026 年生产系统的共识：**能用 RAG 解决的，不用微调**。微调只用于让模型学会一种新的"说话风格"或"输出格式"，而不是灌输事实性知识。

RAG 最朴素的形态：

```
用户问题 → 向量化 → 在向量库中检索 Top-K 相似文档 → 拼接进 Prompt → LLM 生成回答
```

这个朴素版本能跑通 demo，但面试官和生产环境都不会满意——因为它在三个环节都有陷阱。

## 二、陷阱一：切块（Chunking）—— "一刀切"的代价

### 2.1 固定长度切块的问题

最简单的做法：每 N 个字符切一块。问题是文档的语义边界和字符数边界大概率对不上：

```python
# 反面示例：无脑固定长度切块
def naive_chunk(text: str, chunk_size: int = 500) -> list[str]:
    return [text[i:i+chunk_size] for i in range(0, len(text), chunk_size)]

# 假设一段话是：
# "红烧肉的做法：先焯水去腥，然后炒糖色，颜色要炒到枣红色，
#  太浅不上色，太深会发苦。接着下肉块翻炒，加调料，最后小火炖40分钟。"
#
# 如果切块边界刚好落在"太浅不上色，太深"中间，
# 后半句"太深会发苦"被切到下一块，检索到前一块时，
# 语义变成了"颜色要炒到枣红色，太浅不上色"——信息不完整，
# 模型可能会漏掉"炒过头也不行"这个关键约束。
```

### 2.2 语义切块（Semantic Chunking）

按照文档的自然结构切——标题、段落、列表项，保证每一块本身语义完整：

```python
import re

def semantic_chunk_by_heading(markdown_text: str) -> list[dict]:
    """按 Markdown 标题层级切块，每块保留自己的标题上下文"""
    sections = re.split(r'(?=^#{1,3}\s)', markdown_text, flags=re.MULTILINE)
    chunks = []
    for section in sections:
        if not section.strip():
            continue
        lines = section.strip().split('\n')
        title = lines[0] if lines[0].startswith('#') else ""
        chunks.append({
            "title": title,
            "content": section.strip(),
        })
    return chunks
```

### 2.3 Late Chunking（2026 进阶技巧）

传统流程是"先切块，再对每块单独编码"——问题是每块被编码时看不到全文语境，比如某块里的代词"它"指代的是前面段落提到的实体，单独编码时模型不知道"它"是谁。

Late Chunking 反过来：**先对全文做 token 级别的上下文编码，再切块**，每个块的向量是从"已经理解全文语境"的 token 表示中池化得到的，即使切开了，向量依然带着全局语境信息。

```python
# 伪代码示意 late chunking 的思路（真实实现依赖支持长上下文的 embedding 模型）
def late_chunking(text: str, embedding_model, boundaries: list[tuple[int, int]]):
    """
    1. 对整篇文本做一次性 token 级编码（不是逐块编码）
    2. 按照预先定义好的分块边界，对每块对应的 token 向量做平均池化
    """
    token_embeddings = embedding_model.encode_tokens(text)  # 全文级别编码
    chunk_vectors = []
    for start, end in boundaries:
        chunk_vector = token_embeddings[start:end].mean(axis=0)
        chunk_vectors.append(chunk_vector)
    return chunk_vectors
```

### 2.4 切块策略选择表

| 场景 | 推荐策略 |
|------|----------|
| 结构化文档（有标题层级） | 按标题切块 |
| 非结构化长文本（小说、访谈记录） | 语义切块 + 滑动窗口重叠 |
| 代码文件 | 按函数/类切块，保留导入语句作为上下文 |
| 表格/财报数据 | 保留表头，每行或每个逻辑单元作为一块 |
| 对精度要求极高的场景 | Late Chunking |

## 三、陷阱二：检索（Retrieval）—— "唯余弦相似度论"

### 3.1 纯向量检索的局限

向量检索本质是语义相似度匹配，擅长"意思相近"，不擅长"精确匹配"：

```python
# 问题示例：
query = "订单号 A20260315998 的退款进度"
# 向量检索可能找到很多"关于退款流程"的通用文档，
# 但恰好包含这个具体订单号的那条记录，
# 因为订单号是随机字符串，在向量空间里没有明显的"语义位置"，
# 很容易被语义上更"像退款问题"但不含订单号的文档挤掉排名。
```

### 3.2 混合检索（Hybrid Search）

把关键词检索（BM25，擅长精确词匹配）和向量检索（擅长语义匹配）结合：

```python
from rank_bm25 import BM25Okapi
import numpy as np

class HybridRetriever:
    def __init__(self, documents: list[str], embedding_model):
        self.documents = documents
        self.embedding_model = embedding_model
        # BM25 索引（关键词检索）
        tokenized_docs = [doc.split() for doc in documents]
        self.bm25 = BM25Okapi(tokenized_docs)
        # 向量索引（语义检索）
        self.doc_vectors = embedding_model.encode(documents)

    def search(self, query: str, top_k: int = 5) -> list[tuple[str, float]]:
        # 关键词检索得分
        bm25_scores = self.bm25.get_scores(query.split())
        # 向量检索得分（余弦相似度）
        query_vector = self.embedding_model.encode([query])[0]
        vector_scores = np.dot(self.doc_vectors, query_vector) / (
            np.linalg.norm(self.doc_vectors, axis=1) * np.linalg.norm(query_vector)
        )
        # RRF 融合排序：倒数排名融合，而不是直接加权分数
        # 因为 BM25 分数和余弦相似度分数量纲完全不同，直接加权会失真
        bm25_rank = np.argsort(-bm25_scores)
        vector_rank = np.argsort(-vector_scores)

        rrf_scores = {}
        k = 60  # RRF 的平滑常数，业界惯用值
        for rank, idx in enumerate(bm25_rank):
            rrf_scores[idx] = rrf_scores.get(idx, 0) + 1 / (k + rank + 1)
        for rank, idx in enumerate(vector_rank):
            rrf_scores[idx] = rrf_scores.get(idx, 0) + 1 / (k + rank + 1)

        sorted_indices = sorted(rrf_scores.keys(), key=lambda i: -rrf_scores[i])
        return [(self.documents[i], rrf_scores[i]) for i in sorted_indices[:top_k]]
```

**面试考点**：为什么用 RRF 融合而不是直接加权平均？因为 BM25 分数范围不固定（可能是 0-30），余弦相似度固定在 -1 到 1 之间，直接加权会让某一路检索的结果主导排序，RRF 只依赖排名顺序，不依赖具体分数大小，天然解决了量纲不一致的问题。

### 3.3 重排序（Reranking）

向量检索/混合检索召回的是"大致靠谱"的候选集（比如 Top 20），真正决定最终塞给模型哪几条的是重排序模型——用交叉编码器（Cross-Encoder）把 query 和每个候选文档**一起**输入模型编码打分，比向量检索的"各自独立编码再算相似度"精度高得多：

```python
from sentence_transformers import CrossEncoder

class Reranker:
    def __init__(self, model_name: str = "cross-encoder/ms-marco-MiniLM-L-6-v2"):
        self.model = CrossEncoder(model_name)

    def rerank(self, query: str, candidates: list[str], top_k: int = 5) -> list[str]:
        pairs = [[query, doc] for doc in candidates]
        scores = self.model.predict(pairs)
        ranked = sorted(zip(candidates, scores), key=lambda x: -x[1])
        return [doc for doc, score in ranked[:top_k]]

# 典型生产 pipeline：
# 混合检索召回 Top 20 → Rerank 精排 → 取 Top 5 喂给 LLM
```

**为什么不直接用交叉编码器做全库检索？** 因为交叉编码器需要把 query 和每篇文档都拼在一起过一次模型，计算量随文档数线性增长，全库跑一遍代价太高。所以生产架构永远是"向量检索做粗筛（快、召回率高）+ 重排序做精排（慢、精度高）"的两阶段设计，这是检索系统里效率和精度的经典权衡（trade-off）。

## 四、陷阱三：生成（Generation）—— "垃圾进垃圾出"与 Lost in the Middle

### 4.1 检索到的文档不是越多越好

```python
# 反面做法：为了"保险"塞 20 条检索结果进 prompt
context = "\n\n".join(top_20_documents)  # 可能引入大量噪音

# 更好的做法：严格控制精选后的证据数量
context = "\n\n".join(reranked_top_5_documents)
```

Lost in the Middle 现象：模型对长上下文中间部分的信息利用率明显低于开头和结尾。这意味着即使你把正确答案所在的文档塞进了上下文，如果它恰好排在中间，模型也可能"看不见"。工程对策：

1. 把重排序打分最高的文档放在离问题最近的位置（通常是上下文末尾）
2. 严格限制塞入的文档数量，宁可少而精
3. 让模型在生成时明确引用来源（"根据文档 3..."），强制它对齐检索到的证据

### 4.2 检索质量差时如何兜底

```python
def rag_answer(query: str, retriever, llm, relevance_threshold: float = 0.3) -> str:
    results = retriever.search(query, top_k=5)

    # 陷阱：即使检索结果和问题毫不相关，模型也会硬着头皮"编"一个答案
    # 必须显式检查相关性分数，过低就拒绝回答而不是瞎编
    relevant_results = [(doc, score) for doc, score in results if score > relevance_threshold]

    if not relevant_results:
        return "抱歉，知识库中没有找到与您问题相关的信息，无法回答。"

    context = "\n\n".join(doc for doc, _ in relevant_results)
    prompt = f"""请仅根据以下资料回答问题，如果资料不足以回答，请明确说明。

资料：
{context}

问题：{query}"""
    return llm.invoke(prompt)
```

## 五、陷阱四：多跳问题 —— 朴素 RAG 的天花板

朴素 RAG 是"一次检索、一次生成"，遇到需要综合多份文档才能回答的问题就会露馅：

```
用户问题："A 公司 2025 年营收比 B 公司高多少？"
→ 这个问题需要检索两份文档（A 公司财报、B 公司财报），并做数值计算
→ 朴素 RAG 的单次检索大概率只召回其中一份最相关的文档，另一份因为
   查询词侧重点不同而漏检
```

### 5.1 Agentic RAG：把检索变成可以被规划和反思的动作

2026 年的主流解法：让模型自己判断"当前检索到的信息是否足够回答问题"，不够就重新生成检索词再查一轮，这本质上是把 RAG 套进了阶段 2 学过的 ReAct 循环：

```python
from langgraph.graph import StateGraph, END
from typing import TypedDict

class AgenticRAGState(TypedDict):
    question: str
    sub_queries: list[str]
    collected_evidence: list[str]
    is_sufficient: bool
    final_answer: str

def plan_retrieval(state: AgenticRAGState) -> dict:
    """让 LLM 判断需要检索哪些子问题"""
    response = llm.invoke(f"""
将以下问题拆解为需要分别检索的子问题（如果不需要拆解，返回原问题）：
{state['question']}
以 JSON 数组格式返回子问题列表。
""")
    return {"sub_queries": parse_json_list(response.content)}

def retrieve_evidence(state: AgenticRAGState) -> dict:
    evidence = []
    for sub_q in state["sub_queries"]:
        results = retriever.search(sub_q, top_k=3)
        evidence.extend([doc for doc, _ in results])
    return {"collected_evidence": state.get("collected_evidence", []) + evidence}

def check_sufficiency(state: AgenticRAGState) -> dict:
    """让 LLM 判断已收集的证据是否足够回答原问题"""
    response = llm.invoke(f"""
问题：{state['question']}
已收集证据：{state['collected_evidence']}
这些证据是否足够完整回答问题？只回答 yes 或 no。
""")
    return {"is_sufficient": "yes" in response.content.lower()}

def route_after_check(state: AgenticRAGState) -> str:
    if state["is_sufficient"] or len(state.get("collected_evidence", [])) > 15:
        return "generate_answer"  # 加安全上限防止无限检索
    return "plan_retrieval"  # 证据不够，重新规划检索

def generate_answer(state: AgenticRAGState) -> dict:
    response = llm.invoke(f"""
根据以下证据回答问题：
{state['collected_evidence']}
问题：{state['question']}
""")
    return {"final_answer": response.content}

# 组装 Agentic RAG 图
graph = StateGraph(AgenticRAGState)
graph.add_node("plan_retrieval", plan_retrieval)
graph.add_node("retrieve_evidence", retrieve_evidence)
graph.add_node("check_sufficiency", check_sufficiency)
graph.add_node("generate_answer", generate_answer)

graph.set_entry_point("plan_retrieval")
graph.add_edge("plan_retrieval", "retrieve_evidence")
graph.add_edge("retrieve_evidence", "check_sufficiency")
graph.add_conditional_edges("check_sufficiency", route_after_check)
graph.add_edge("generate_answer", END)

agentic_rag = graph.compile()
```

这套设计和第 25 节要讲的 GraphRAG 是解决多跳问题的两条不同路径：Agentic RAG 靠"多轮检索+反思"逼近答案，GraphRAG 靠"预先构建实体关系图"直接支持多跳遍历，两者也可以组合使用。

## 六、RAG 架构演进全景（面试参考）

| 代际 | 特征 | 局限 |
|------|------|------|
| Naive RAG | 固定切块 + 单次向量检索 + 直接拼接生成 | 精度低，无法处理多跳问题 |
| Advanced RAG | 语义切块 + 混合检索 + 重排序 | 生产默认起点，多数场景够用 |
| Agentic RAG | 检索动作可规划、可反思、多轮迭代 | 延迟和成本更高，需要控制迭代上限 |
| GraphRAG | 知识图谱 + 图遍历，专攻多跳推理 | 图谱构建成本高，见第 25 节 |

**面试标准答法**：我们不会一上来就上 GraphRAG 或复杂的 Agentic RAG，而是先把 Advanced RAG（语义切块+混合检索+重排序）的基本功打扎实，用评估指标（见第 27 节）量化效果，只有当数据证明现有方案确实在多跳问题上翻车，才引入更复杂的架构，这是避免过度工程化的正确态度。

## 七、练习题

### 概念理解

1. 为什么 RRF 融合排序比直接加权平均更适合融合 BM25 和向量检索的结果？
2. Lost in the Middle 现象对 RAG 的 prompt 拼接策略有什么启发？
3. Late Chunking 和普通语义切块的本质区别是什么？

### 动手编码

4. 实现一个简单的语义切块函数，按照 Markdown 的二级标题切分一篇文档，并保留每块的标题路径（比如"第二章 > 2.1 节"）作为元数据。

5. 用 `rank_bm25` 和任意 embedding 模型（如 `sentence-transformers`），实现本节的 `HybridRetriever`，用一组测试问题对比"纯向量检索"和"混合检索"在包含精确编号/术语的问题上的召回差异。

6. 扩展 `rag_answer` 函数，加入"引用来源"功能——让模型回答时标注每句话引用了第几条检索证据，便于用户溯源验证。

### 面试模拟

7. "你之前做的 RAG 项目，检索精度不够怎么排查？" 参考答法：分层排查——先看切块是否语义完整（打印检索到的原始 chunk 看是否可读），再看是纯向量检索的召回问题还是排序问题（引入混合检索和 reranker 分别测试），最后看生成阶段是否存在 lost in the middle（调整证据数量和位置测试）。

8. "什么时候应该用 GraphRAG 而不是普通 RAG？" 参考答法：当业务问题本质上是关系型、多跳型的（比如"这两个人有没有共同投资过同一家公司"），普通向量检索很难把分散在多篇文档里的实体关系拼起来，这时候预先构建知识图谱、支持图遍历查询会比多轮 agentic 检索更稳定、更可控。

## 八、小结

这一节把 RAG 从"检索+生成"两步走的简单印象，拆解成切块、检索、生成三层各自的陷阱：切块要防止语义被"一刀切"破坏，检索要靠混合检索和重排序弥补纯向量匹配的短板，生成要防止垃圾上下文和 lost in the middle 拖累回答质量，而多跳问题则是朴素 RAG 的天花板，需要 Agentic RAG 或 GraphRAG 来突破。
