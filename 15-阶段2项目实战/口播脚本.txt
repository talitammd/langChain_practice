面试官说："前面问了你 ReAct、规划、记忆、工具编排、上下文工程、反思修正，你能不能把这些串起来，给我讲讲你项目里的 Agent 是怎么跑的？"如果你只能孤立地背概念，这一问就露馅了。今天这一节是阶段 2 的项目实战，我们把前面七节的内容全部整合到一个能跑的 Agent 里。

先说项目背景。我们要做一个"智能研究助手"——用户提出一个研究问题，比如"对比 React 和 Vue 在 2026 年的性能表现"，Agent 自主完成：拆解研究计划、搜索资料、整理数据、生成报告。整个过程中要处理工具失败、上下文超限、中间结果出错等各种真实问题。

整体架构是分层的。最上层是 Plan-and-Execute：Planner 把研究任务拆成子任务——搜 React 性能数据、搜 Vue 性能数据、搜对比基准测试、综合分析写报告。每个子任务交给一个独立的执行单元。

每个执行单元内部跑 ReAct 循环。拿"搜 React 性能数据"这个子任务来说：Agent 先思考该搜什么关键词，调用搜索工具，观察返回结果，发现信息不够再换个关键词搜，循环到拿到足够数据为止。这里就用到第 9 节的 Thought-Action-Observation 循环。

搜索工具可能失败——网络超时、API 限流、返回空结果。这就是第 12 节的内容：瞬时错误用指数退避重试，连续失败触发熔断器跳过该工具，降级到备用搜索源。工具返回的原始数据要做错误信息翻译，把技术报错转成 Agent 能理解的提示。

每个子任务执行完产生大量中间数据——搜索结果、网页内容、提取的表格。全堆在上下文里很快超限。这里用第 13 节的上下文工程：Write 操作把中间结果存到外部文件，Select 操作在需要时检索相关部分，Compress 操作把冗长的网页内容压缩成要点摘要。每个子任务用独立的上下文窗口——这就是 Isolate。

子任务之间还要共享信息。比如"搜 React 数据"的子任务发现了某个基准测试网站，"搜对比基准测试"的子任务应该能用到这个信息。这里用第 11 节的记忆系统：关键发现写入长期记忆，下一个子任务开始时用向量检索把相关记忆取出来塞进上下文。

最后是第 14 节的反思机制。Agent 生成研究报告后，用 Reflexion 机制自我检查：报告里的数据有没有来源支撑？结论有没有逻辑跳跃？如果发现问题，生成具体反思——"第三段引用的性能数据没有标注来源"——存入情景记忆，修改后重新检查，循环到通过或达到最大重试次数。

把整个流程串一遍。用户提问 → Planner 拆成 4 个子任务 → 每个子任务独立跑 ReAct 循环（搜索、提取、整理）→ 工具失败自动重试和降级 → 中间结果 Write 到外部不占上下文 → 子任务间通过记忆系统共享关键发现 → 所有子任务完成后汇总 → Reflexion 反思检查报告质量 → 不满意就改 → 输出最终报告。

面试时怎么讲这个项目？关键是体现你的工程判断力。不要平铺直叙说"我用了 ReAct 加 Plan-and-Execute"，而是讲权衡：为什么用 Plan-and-Execute 而不是纯 ReAct——因为任务太长，纯 ReAct 的上下文会爆。为什么子任务用独立上下文——Isolate 避免信息互相干扰。为什么反思用外部验证而不是自评——因为纯自评有确认偏差。每个技术选型背后都有"为什么这么选"的思考过程，这才是面试官想听的。
