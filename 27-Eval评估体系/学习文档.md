# 第27节：Eval 评估体系 — 用数据证明 Agent 变好了，而不是"我感觉"

## 一、为什么大模型应用需要一套新的测试方法论

传统软件测试：输入固定、输出固定，字符串相等即通过。

大模型应用：同一个输入两次调用，输出的用词可能完全不同但语义等价，无法用精确匹配判断对错。

```python
# 传统单元测试的思路在这里失效
def test_add():
    assert add(1, 2) == 3  # 精确匹配，非黑即白

# 大模型场景做不到这样测试
def test_agent_response():
    response = agent.ask("红烧肉怎么做")
    assert response == "标准答案文本"  # ❌ 几乎不可能完全匹配
```

这就是为什么 2026 年 AI 团队的成熟度分水岭，是有没有一套科学的 **Eval（评估）体系**，而不是靠工程师"人工抽查感觉一下"。

## 二、地基：构建评估数据集

### 2.1 数据集的构成

```python
from pydantic import BaseModel
from enum import Enum

class TestCaseCategory(str, Enum):
    TYPICAL = "typical"          # 典型场景，覆盖核心功能
    EDGE_CASE = "edge_case"      # 边界情况，比如空输入、超长输入
    REGRESSION = "regression"    # 回归用例，之前踩过的坑对应的用例
    ADVERSARIAL = "adversarial"  # 对抗性用例，故意刁难系统的输入

class EvalTestCase(BaseModel):
    case_id: str
    category: TestCaseCategory
    input_query: str
    expected_behavior: str  # 不是精确答案，而是"期望满足的行为标准"
    ground_truth_context: list[str] = []  # RAG 场景下，期望被检索到的证据
    metadata: dict = {}
```

### 2.2 数据来源

| 来源 | 说明 |
|------|------|
| 真实用户历史查询 | 最有代表性，反映真实使用分布 |
| 人工构造的边界案例 | 覆盖系统设计时预想到的极端情况 |
| 历史 bug 对应的回归用例 | 每修一个 bug，补一条对应的测试用例，防止复发 |
| 对抗性测试 | 故意构造的诱导性、模糊性输入，测试系统的鲁棒性 |

**关键认知**：评估数据集不是一次性写完的，而是随着系统迭代持续增长的活文档，本质上扮演的角色和传统软件的单元测试集一样，区别只是评判标准从"精确匹配"变成了"行为标准打分"。

## 三、LLM-as-Judge：用模型评判模型

### 3.1 基本思路

用一个（通常更强的）大模型，根据清晰的评分标准，对被测系统的输出打分并给出理由：

```python
from pydantic import BaseModel, Field

class JudgeVerdict(BaseModel):
    score: int = Field(..., description="1-5 分，5分最好")
    reasoning: str = Field(..., description="打分理由")
    passed: bool = Field(..., description="是否达到及格线")


class LLMJudge:
    def __init__(self, judge_llm):
        self.judge_llm = judge_llm

    def evaluate(self, test_case: EvalTestCase, actual_response: str) -> JudgeVerdict:
        prompt = f"""你是一个严格的评估员，请根据以下标准评估回答质量：

评分标准：
1. 是否准确回答了用户问题的核心诉求
2. 是否存在编造、与事实不符的内容
3. 语言是否清晰、逻辑是否连贯
4. 是否符合期望行为："{test_case.expected_behavior}"

用户问题：{test_case.input_query}
系统实际回答：{actual_response}

请给出 1-5 分的评分，5分代表完全符合标准，1分代表严重不符合，并说明理由。"""

        return self.judge_llm.with_structured_output(JudgeVerdict).invoke(prompt)
```

### 3.2 评判模型本身的可靠性要单独验证

这是最容易被忽略、但面试官最爱追问的细节：**用来打分的模型本身靠不靠谱，需要先验证**。

```python
def validate_judge_reliability(judge: LLMJudge, human_labeled_cases: list[dict]) -> float:
    """
    human_labeled_cases: 一批人工标注过"通过/不通过"的黄金标准数据
    用来验证 LLM Judge 的判断和人工判断的一致率
    """
    agreements = 0
    for case in human_labeled_cases:
        verdict = judge.evaluate(case["test_case"], case["response"])
        if verdict.passed == case["human_label"]:
            agreements += 1

    agreement_rate = agreements / len(human_labeled_cases)
    return agreement_rate

# 面试考点：一致率低于什么阈值就不能信任这套评估体系？
# 业界经验值通常要求 LLM Judge 和人工标注的一致率达到 80% 以上才可信，
# 一致率不够高，意味着这把"尺子"本身是歪的，用它衡量系统改进毫无意义。
```

### 3.3 常见的打分偏差（Judge Bias）

| 偏差类型 | 说明 |
|---------|------|
| 位置偏差 | 在对比两个答案时，模型倾向于偏好排在前面的那个 |
| 长度偏差 | 模型倾向于给更长的回答打更高分，即使信息密度更低 |
| 自我偏好偏差 | 如果评判模型和被评模型是同系列，容易给"风格相似"的回答更高分 |

工程对策：对比评估时随机打乱顺序、多次评估取平均、必要时换用不同厂商的模型做交叉验证。

## 四、轨迹评估（Trajectory Evaluation）

### 4.1 为什么终点正确不代表过程正确

Agent 完成任务往往要走多步：调用工具、做决策、再调用工具。**最终答案对，不代表中间过程是对的**——可能是蒙对的，也可能绕了很多弯路才碰巧撞对。

```python
from pydantic import BaseModel

class AgentStep(BaseModel):
    step_index: int
    action_type: str  # "tool_call" / "reasoning" / "final_answer"
    tool_name: str | None = None
    tool_args: dict | None = None
    reasoning: str | None = None

class TrajectoryEvalResult(BaseModel):
    is_final_answer_correct: bool
    is_trajectory_efficient: bool  # 有没有多余的、绕弯路的步骤
    has_incorrect_tool_calls: bool  # 工具调用参数是否有误
    unnecessary_steps: list[int]  # 哪些步骤是多余的


def evaluate_trajectory(judge_llm, task: str, trajectory: list[AgentStep], final_answer: str) -> TrajectoryEvalResult:
    trajectory_text = "\n".join(
        f"步骤{s.step_index}: {s.action_type}"
        + (f" 调用工具 {s.tool_name}，参数 {s.tool_args}" if s.tool_name else "")
        + (f" 推理：{s.reasoning}" if s.reasoning else "")
        for s in trajectory
    )

    prompt = f"""任务：{task}

Agent 执行轨迹：
{trajectory_text}

最终答案：{final_answer}

请评估：
1. 最终答案是否正确解决了任务
2. 执行路径是否高效（有没有多余或重复的步骤）
3. 工具调用的参数是否正确、合理
4. 指出具体哪些步骤是不必要的（按步骤编号列出）
"""
    return judge_llm.with_structured_output(TrajectoryEvalResult).invoke(prompt)
```

**面试考点**：轨迹评估能帮你精确定位问题出在哪一层——是规划环节想错了方向，还是工具调用参数写错了，还是最终生成环节没有正确利用前面收集的信息。这比只看"最终答案对不对"这一个维度的诊断能力强得多。

## 五、RAG 专项评估：RAGAS 四大指标

针对 RAG 系统，业界最常用的评估框架 RAGAS 提出四个核心指标：

```python
from pydantic import BaseModel

class RAGASMetrics(BaseModel):
    faithfulness: float       # 忠实度：回答是否忠于检索到的证据，有没有编造内容
    answer_relevancy: float   # 答案相关性：回答是否真正对上了用户的问题
    context_precision: float  # 上下文精确率：检索回来的证据里，有多少是真正相关的
    context_recall: float     # 上下文召回率：真正需要的证据，有没有被完整检索到


def compute_faithfulness(judge_llm, answer: str, retrieved_context: list[str]) -> float:
    """忠实度：把回答拆解成若干个论断，逐条检查是否能在检索证据中找到支撑"""
    claims_prompt = f"将以下回答拆解为独立的事实性论断，每条一行：\n{answer}"
    claims = judge_llm.invoke(claims_prompt).content.split("\n")

    supported_count = 0
    for claim in claims:
        check_prompt = f"""证据：{retrieved_context}
论断：{claim}
这个论断能否由上述证据支撑？只回答 yes 或 no。"""
        result = judge_llm.invoke(check_prompt).content
        if "yes" in result.lower():
            supported_count += 1

    return supported_count / len(claims) if claims else 0.0


def compute_context_precision(judge_llm, question: str, retrieved_context: list[str]) -> float:
    """上下文精确率：检索到的证据里，有多少条真正和问题相关"""
    relevant_count = 0
    for ctx in retrieved_context:
        prompt = f"问题：{question}\n证据：{ctx}\n这条证据是否与回答该问题相关？只回答 yes 或 no。"
        result = judge_llm.invoke(prompt).content
        if "yes" in result.lower():
            relevant_count += 1
    return relevant_count / len(retrieved_context) if retrieved_context else 0.0
```

### 5.1 四个指标的诊断价值

| 指标低 | 说明问题出在哪 |
|--------|--------------|
| 忠实度低 | 生成环节在编造内容，即使证据检索对了，模型也没有严格依据证据回答 |
| 答案相关性低 | 生成环节偏题，没有真正对上用户问题的核心诉求 |
| 上下文精确率低 | 检索环节召回了大量不相关文档，需要优化检索或加强重排序 |
| 上下文召回率低 | 检索环节漏掉了关键证据，需要优化切块策略或检索词生成 |

这四个指标能帮你精确定位问题出在检索环节还是生成环节，而不是笼统地说"回答不准"就去瞎调整。

## 六、CI-Gated Eval：把评估接入持续集成

Eval 不是写完跑一次就完事，而是要在每次改动后自动重跑，防止"按下葫芦浮起瓢"：

```python
from dataclasses import dataclass


@dataclass
class EvalGateConfig:
    min_pass_rate: float = 0.85
    min_faithfulness: float = 0.8
    min_context_recall: float = 0.75


class EvalGate:
    """CI 流程里的评估关卡：跑完整个评估数据集，任何一项指标低于阈值就拦截本次变更"""

    def __init__(self, judge: LLMJudge, config: EvalGateConfig):
        self.judge = judge
        self.config = config

    def run(self, test_cases: list[EvalTestCase], system_under_test) -> dict:
        results = []
        for case in test_cases:
            response = system_under_test.ask(case.input_query)
            verdict = self.judge.evaluate(case, response["answer"])
            results.append({"case_id": case.case_id, "verdict": verdict})

        pass_rate = sum(1 for r in results if r["verdict"].passed) / len(results)

        report = {
            "pass_rate": pass_rate,
            "total_cases": len(test_cases),
            "failed_cases": [r["case_id"] for r in results if not r["verdict"].passed],
            "gate_passed": pass_rate >= self.config.min_pass_rate,
        }
        return report


# 在 CI 脚本中的使用方式（伪代码）：

# if not report["gate_passed"]:
#     raise SystemExit("Eval gate failed，本次变更导致回归，禁止合并")
```

**工程价值**：每次改了 prompt、换了模型、调整了检索策略，自动跑一遍评估数据集，看指标是涨是跌，这在没有传统单元测试保护的大模型应用开发里，是防止"改好了 A 问题却搞坏了 B 问题"的关键防线。

## 七、面试高频问答

**Q：怎么证明你优化后的 Agent 比之前更好？**
A：靠固定的评估数据集加 LLM-as-Judge 打分，对比优化前后的通过率和各项细分指标（如 RAGAS 四项指标），而不是靠人工抽查几个案例的主观印象。同时要保证这个评估数据集覆盖了典型场景、边界情况和历史回归用例，否则"优化后变好"的结论可能只在评估集覆盖到的场景里成立。

**Q：LLM-as-Judge 本身靠谱吗，怎么验证？**
A：需要用一批人工标注的黄金标准数据，检验 LLM Judge 的打分和人工判断的一致率，业界经验值要求达到 80% 以上才可信。同时要警惕位置偏差、长度偏差等已知的评判偏差，通过随机打乱顺序、多次评估取平均等手段缓解。

**Q：Eval 和传统软件测试最大的区别是什么？**
A：传统测试是确定性的精确匹配，Eval 面对的是非确定性输出，需要用"行为标准打分"代替"字符串相等"，而且需要额外验证评判者（LLM Judge）本身的可靠性，这是传统测试里不存在的一层复杂度。

## 八、练习题

### 概念理解

1. 为什么终点式的整体打分不足以诊断 Agent 系统的问题，轨迹评估补充了什么？
2. RAGAS 的忠实度和答案相关性有什么区别？举一个"忠实度高但相关性低"的例子。
3. LLM Judge 的位置偏差具体是怎么产生的，怎么用实验设计消除它的影响？

### 动手编码

4. 实现本节的 `LLMJudge` 类和 `validate_judge_reliability` 函数，用 5-10 条你自己构造的测试用例和人工标注，验证某个 LLM 作为评判者的一致率。

5. 实现 `compute_faithfulness` 和 `compute_context_precision` 两个 RAGAS 指标，接入第26节做的 EnterpriseKB 项目，跑一遍看当前系统在这两个指标上的表现。

6. 实现一个简化版的 `EvalGate`，构造一批回归测试用例，模拟"改动 A 导致某个历史 bug 复现"的场景，验证 Gate 能否正确拦截。

### 面试模拟

7. "评估数据集应该多大规模？" 参考答法：没有绝对数字，但要保证四类用例（典型场景、边界情况、回归用例、对抗性用例）都有覆盖，规模上从几十条起步就能发现明显问题，生产级系统的评估集通常会扩展到几百上千条，并随着新问题的发现持续增长。

8. "如果没有资源做人工标注怎么办？" 参考答法：可以先用少量高质量人工标注验证 LLM Judge 的可靠性，一旦验证通过，后续大规模评估可以主要依赖 LLM Judge，只对新增的、有争议的、评分边界的用例做抽样人工复核，把人力成本控制在可持续范围内。

## 九、小结

这一节讲清楚了"证明 Agent 变好了"这件事的完整方法论：先构建覆盖典型场景、边界情况、回归用例的评估数据集，用 LLM-as-Judge 打分并验证评判者本身的可靠性，用轨迹评估诊断多步 Agent 的中间过程而不只看终点，用 RAGAS 四大指标精确定位 RAG 系统的问题出在检索还是生成，最后把整套评估接入 CI 流程做持续防护。这是"用数据说话"而不是"我感觉"的核心工程能力。
