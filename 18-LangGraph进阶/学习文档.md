# 第18节：LangGraph 进阶 — 条件分支、循环、人工介入（Human-in-the-loop）

## 一、本节定位

上节掌握了 LangGraph 的三件套：State、Node、Edge，能写一个基础的 ReAct Agent。但生产中你会遇到更复杂的场景：根据不同结果走不同处理分支、某些步骤需要人工确认才能继续、一个大图里嵌套小图。本节目标：掌握 LangGraph 的进阶模式——**条件分支、循环控制、Human-in-the-loop、子图**，让你的 Agent 图能应对真实业务需求。

---

## 二、条件分支：让 Agent 走不同路径

### 2.1 多路条件分支

上节的条件边只有两条路（去 Tools 或 END），真实场景往往需要多路分支：

```python
from langgraph.graph import StateGraph, END

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]
    task_type: str  # 任务类型：research / code / general

def classify_task(state: AgentState) -> dict:
    """分类节点：判断任务类型"""
    response = model.invoke([
        SystemMessage(content="判断用户意图，只回复: research/code/general"),
        state["messages"][-1]
    ])
    return {"task_type": response.content.strip()}

def research_node(state: AgentState) -> dict:
    """研究类任务处理"""
    # 调用搜索工具、整理信息...
    return {"messages": [AIMessage(content="研究结果...")]}

def code_node(state: AgentState) -> dict:
    """编程类任务处理"""
    # 生成代码、执行测试...
    return {"messages": [AIMessage(content="代码结果...")]}

def general_node(state: AgentState) -> dict:
    """通用对话处理"""
    response = model.invoke(state["messages"])
    return {"messages": [response]}

# 路由函数
def route_task(state: AgentState) -> str:
    task_type = state.get("task_type", "general")
    if task_type == "research":
        return "research"
    elif task_type == "code":
        return "code"
    return "general"

# 构建图
graph = StateGraph(AgentState)
graph.add_node("classify", classify_task)
graph.add_node("research", research_node)
graph.add_node("code", code_node)
graph.add_node("general", general_node)

graph.set_entry_point("classify")
graph.add_conditional_edges("classify", route_task)  # 三路分支
graph.add_edge("research", END)
graph.add_edge("code", END)
graph.add_edge("general", END)

app = graph.compile()
```

图结构：
```
              ┌───────────┐
              │  classify  │
              └─────┬─────┘
          ┌─────────┼─────────┐
          ▼         ▼         ▼
    ┌──────────┐ ┌──────┐ ┌─────────┐
    │ research │ │ code │ │ general │
    └────┬─────┘ └──┬───┘ └────┬────┘
         └──────────┼──────────┘
                    ▼
                   END
```

## 三、循环控制：防止 Agent 死循环

### 3.1 计数器限制

最基础的方式——在 State 中加计数器：

```python
class AgentState(TypedDict):
    messages: Annotated[list, add_messages]
    iteration_count: int

def agent_node(state: AgentState) -> dict:
    response = model.invoke(state["messages"])
    return {
        "messages": [response],
        "iteration_count": state.get("iteration_count", 0) + 1
    }

def should_continue(state: AgentState) -> str:
    # 超过 10 轮强制停止
    if state.get("iteration_count", 0) >= 10:
        return "force_end"
    last_msg = state["messages"][-1]
    if hasattr(last_msg, "tool_calls") and last_msg.tool_calls:
        return "tools"
    return END

def force_end_node(state: AgentState) -> dict:
    """强制结束时给用户一个交代"""
    return {"messages": [AIMessage(content="已达到最大处理轮次，请简化你的问题后重试。")]}

graph.add_node("force_end", force_end_node)
graph.add_conditional_edges("agent", should_continue)
graph.add_edge("force_end", END)
```

### 3.2 使用 LangGraph 内置的 recursion_limit

```python
# 编译时设置全局递归限制
app = graph.compile()

# 运行时通过 config 设置
result = app.invoke(
    {"messages": [HumanMessage(content="...")]},
    config={"recursion_limit": 25}  # 最多经过 25 个节点
)
```

**面试要点**：两种方式的区别——`recursion_limit` 是全局的节点执行次数上限，计数器是可以针对特定行为（如工具调用）的细粒度控制。生产中通常两者结合使用。

## 四、Human-in-the-loop：人工介入

### 4.1 为什么需要人工介入

Agent 做的某些操作不可逆——发邮件、转账、删除文件。你需要在关键步骤暂停图执行，等人确认后再继续。

### 4.2 interrupt() — LangGraph 的原生中断

```python
from langgraph.types import interrupt, Command
from langgraph.checkpoint.memory import MemorySaver

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]
    pending_action: dict  # 待确认的操作

def agent_node(state: AgentState) -> dict:
    response = model.invoke(state["messages"])
    return {"messages": [response]}

def tool_node(state: AgentState) -> dict:
    last_message = state["messages"][-1]
    results = []
    for call in last_message.tool_calls:
        # 如果是危险操作，中断等人确认
        if call["name"] in ["send_email", "delete_file", "transfer_money"]:
            # interrupt() 会暂停图执行，返回给调用方
            approval = interrupt({
                "question": f"确认执行 {call['name']}？参数：{call['args']}",
                "tool_call": call
            })
            if approval != "yes":
                results.append(ToolMessage(
                    content=f"用户拒绝了 {call['name']} 操作",
                    tool_call_id=call["id"]
                ))
                continue
        # 执行工具
        func = tools[call["name"]]
        result = func(**call["args"])
        results.append(ToolMessage(content=str(result), tool_call_id=call["id"]))
    return {"messages": results}

# 编译时必须带 Checkpointer（中断恢复依赖状态持久化）
checkpointer = MemorySaver()
app = graph.compile(checkpointer=checkpointer)

# === 第一次调用：会在危险操作处中断 ===
config = {"configurable": {"thread_id": "user-456"}}
result = app.invoke(
    {"messages": [HumanMessage(content="帮我删除 /tmp/test.txt")]},
    config=config
)
# 此时 app 会暂停在 interrupt() 处
# result 包含中断信息：确认执行 delete_file？

# === 人工确认后恢复 ===
# 用 Command 传入人工决策，恢复图执行
result = app.invoke(
    Command(resume="yes"),  # 传入 "yes" 恢复执行
    config=config
)
# 图从中断点继续执行 delete_file
```

### 4.3 Human-in-the-loop 的三种模式

| 模式 | 实现 | 适用场景 |
|------|------|---------|
| 审批模式 | `interrupt()` 在工具执行前暂停 | 危险操作确认（删除、转账） |
| 编辑模式 | `interrupt()` 让人修改 State 后继续 | 修改 Agent 的计划或工具参数 |
| 反馈模式 | 中断后收集人的反馈，塞入 messages | Agent 输出不满意，给修改意见 |

## 五、子图（Subgraph）：图中嵌套图

### 5.1 为什么要用子图

当你的 Agent 图变得很大（20+ 个节点），一张图维护不动。子图把复杂逻辑封装成独立模块，主图只需要知道子图的输入和输出：

```python
# === 定义子图：研究子流程 ===
class ResearchState(TypedDict):
    query: str
    sources: list[str]
    report: str

def search_node(state: ResearchState) -> dict:
    results = search_web(state["query"])
    return {"sources": results}

def summarize_node(state: ResearchState) -> dict:
    summary = model.invoke(f"总结以下资料：{state['sources']}")
    return {"report": summary.content}

research_graph = StateGraph(ResearchState)
research_graph.add_node("search", search_node)
research_graph.add_node("summarize", summarize_node)
research_graph.set_entry_point("search")
research_graph.add_edge("search", "summarize")
research_graph.add_edge("summarize", END)
research_subgraph = research_graph.compile()

# === 在主图中使用子图 ===
class MainState(TypedDict):
    messages: Annotated[list, add_messages]
    research_result: str

def call_research(state: MainState) -> dict:
    """调用研究子图"""
    query = state["messages"][-1].content
    result = research_subgraph.invoke({"query": query, "sources": [], "report": ""})
    return {"research_result": result["report"]}

main_graph = StateGraph(MainState)
main_graph.add_node("research", call_research)
# ... 其他节点
```

### 5.2 子图的状态隔离

子图有自己独立的 State，不会污染主图的 State。这正是上下文工程中"Isolate"操作的工程实现——每个子任务独立上下文窗口，互不干扰。

## 六、Command API（2025+ 新特性）

LangGraph 在 2025 年引入了 `Command` 对象，让节点可以同时更新状态和指定下一个节点：

```python
from langgraph.types import Command

def agent_node(state: AgentState) -> Command:
    response = model.invoke(state["messages"])
    
    if response.tool_calls:
        # 更新状态 + 指定去 tools 节点
        return Command(
            update={"messages": [response]},
            goto="tools"
        )
    else:
        # 更新状态 + 结束
        return Command(
            update={"messages": [response]},
            goto=END
        )
```

**Command 的优势**：把"更新状态"和"决定路由"合并到一个返回值里，不再需要单独的条件边函数。代码更紧凑、逻辑更集中。

## 七、实战：带人工审批的自动化邮件 Agent

```python
"""
完整示例：用户说"给 Alice 发邮件说明天开会"
Agent 生成邮件内容 → 人工审批 → 发送或修改
"""
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, END, add_messages
from langgraph.types import interrupt, Command
from langgraph.checkpoint.memory import MemorySaver
from langchain_core.messages import HumanMessage, AIMessage, SystemMessage

class EmailAgentState(TypedDict):
    messages: Annotated[list, add_messages]
    email_draft: dict    # {"to": str, "subject": str, "body": str}
    approved: bool

def draft_email(state: EmailAgentState) -> dict:
    """生成邮件草稿"""
    response = model.invoke([
        SystemMessage(content="""根据用户指令生成邮件。返回 JSON：
        {"to": "收件人", "subject": "主题", "body": "正文"}"""),
        state["messages"][-1]
    ])
    import json
    draft = json.loads(response.content)
    return {"email_draft": draft}

def review_email(state: EmailAgentState) -> dict:
    """人工审批"""
    draft = state["email_draft"]
    decision = interrupt({
        "message": "请审批以下邮件草稿：",
        "draft": draft,
        "options": ["approve", "reject", "edit"]
    })
    
    if decision == "approve":
        return {"approved": True}
    elif decision == "reject":
        return {"approved": False, "messages": [AIMessage(content="邮件已取消发送。")]}
    else:
        # decision 是修改后的草稿
        return {"email_draft": decision, "approved": True}

def send_email(state: EmailAgentState) -> dict:
    """发送邮件"""
    draft = state["email_draft"]
    # 实际调用邮件 API
    result = f"邮件已发送给 {draft['to']}，主题：{draft['subject']}"
    return {"messages": [AIMessage(content=result)]}

def route_after_review(state: EmailAgentState) -> str:
    if state.get("approved"):
        return "send"
    return END

# 组装图
graph = StateGraph(EmailAgentState)
graph.add_node("draft", draft_email)
graph.add_node("review", review_email)
graph.add_node("send", send_email)

graph.set_entry_point("draft")
graph.add_edge("draft", "review")
graph.add_conditional_edges("review", route_after_review)
graph.add_edge("send", END)

app = graph.compile(checkpointer=MemorySaver())

# 使用
config = {"configurable": {"thread_id": "email-001"}}

# 第一次调用：生成草稿并中断在审批
result = app.invoke(
    {"messages": [HumanMessage(content="给 alice@example.com 发邮件说明天上午十点开会")]},
    config=config
)
# 中断，返回草稿等待审批

# 审批通过
result = app.invoke(Command(resume="approve"), config=config)
# 邮件发送成功
```

## 九、小结 & 下节预告

LangGraph 进阶的核心是三个能力：**条件分支让图能动态路由、Human-in-the-loop 让关键操作有人兜底、子图让复杂系统可拆解可维护**。加上 Command API 把状态更新和路由决策合并，你已经具备了用 LangGraph 搭建生产级 Agent 系统的全部工具。

到这里 LangGraph 的编排能力讲完了，但 Agent 要真正"干活"还需要连接外部工具和数据源。每个工具都自己写接口太累了——有没有标准化的协议让 Agent 即插即用地接入任何工具？有，它叫 MCP，Model Context Protocol，2026 年面试必考。下节课我们拆解 MCP。

## 十、答案要点

<details>
<summary>概念自测参考答案</summary>

**1.** 审批模式：用于不可逆操作（发邮件、转账、删除），Agent 执行前暂停等人确认；编辑模式：用于 Agent 生成的内容需要人工修改的场景（邮件草稿、计划调整），人可以直接改 State 里的数据；反馈模式：Agent 输出不够好，人给出文字反馈塞回 messages，Agent 重新生成。

**2.** `interrupt()` 暂停图执行后，图的当前状态必须被保存下来，否则恢复时无法知道执行到了哪一步。Checkpointer 正是做状态持久化的组件。没有 Checkpointer，interrupt 后状态丢失，无法恢复。

**3.** 子图有独立的 State，子图内部的中间数据不会污染主图的 State，避免了状态爆炸和命名冲突。这对应上下文工程中的 Isolate 操作——给每个子任务独立的上下文窗口，互不干扰。

**4.** Command 对象把状态更新和路由决策合并在节点返回值里，逻辑更集中、代码更紧凑；缺点是路由逻辑分散在各个节点中，图的整体流转不容易从外部一眼看清。条件边把路由逻辑集中在一个函数里，图结构更清晰；缺点是需要额外定义路由函数。

</details>

**5.** 带审批的代码执行 Agent：
```python
class CodeAgentState(TypedDict):
    messages: Annotated[list, add_messages]
    generated_code: str
    execution_result: str

def generate_code(state: CodeAgentState) -> dict:
    response = model.invoke([
        SystemMessage(content="根据用户需求生成 Python 代码，只输出代码不要解释"),
        state["messages"][-1]
    ])
    return {"generated_code": response.content}

def review_code(state: CodeAgentState) -> dict:
    approval = interrupt({
        "message": "请审批以下代码：",
        "code": state["generated_code"],
        "options": ["approve", "reject"]
    })
    if approval == "approve":
        return {}
    return {"messages": [AIMessage(content="代码已被拒绝执行。")]}

def execute_code(state: CodeAgentState) -> dict:
    import subprocess
    result = subprocess.run(
        ["python", "-c", state["generated_code"]],
        capture_output=True, text=True, timeout=10
    )
    output = result.stdout if result.returncode == 0 else f"Error: {result.stderr}"
    return {"execution_result": output, "messages": [AIMessage(content=output)]}
```

**6.** 修改后再审循环：在 review 节点中，如果选择 edit，Command(goto="review") 回到自身，形成循环直到 approve 或 reject。
