# 第05节 · Function Calling / Tool Use 原理

> 配套学习文档｜面试导向｜含代码示例与练习题

---

## 一、本节定位：Agent 真正长出"手"的那一刻

上一节我们让模型能稳定吐出结构化数据了，但那还只是"动嘴"。Agent 之所以能查实时天气、能下单、能操作数据库，靠的是 **Function Calling（工具调用，Claude 称 Tool Use）**。这是 LLM 从"只会输出文本"跨到"能调用外部系统"的关键一步，也是当前所有主流 Agent 的核心基础设施——OpenAI、Claude、DeepSeek 都原生支持。

这一节最重要的，是先破掉一个**几乎人人都踩的面试误区**，再把完整的调用机制、并行调用、可靠性与安全四件事讲透。

---

## 二、核心知识讲解

### 2.1 最关键的认知：模型不执行函数

> **模型从不真正执行任何函数。它只输出一个结构化的"调用请求"，真正干活的是你的应用代码。**

很多人面试张口就说"模型调用了天气接口"——这一句就暴露了没懂原理。准确的说法是：模型**生成了一个 tool_call**，里面写着"我想调 `get_weather`，参数 `city="北京"`"，然后你的代码负责真正去执行它。

记住这句话，面试基本过半。模型负责"动嘴"（决定调谁、抽出参数），你的代码负责"动手"（执行、回填结果）。

### 2.2 完整流程：三轮对话闭环

Function Calling 本质是一个**三轮对话**的闭环：

| 轮次             | 谁在做    | 做什么                                        |
| -------------- | ------ | ------------------------------------------ |
| **第 1 轮 · 发问** | 你 → 模型 | 把工具定义（JSON Schema）+ 用户问题一起发给模型             |
| **第 2 轮 · 抽参** | 模型 → 你 | 模型不直接回答，返回 `tool_calls`：要调的函数名 + 从问句里抽出的参数 |
| **第 3 轮 · 回填** | 你 → 模型 | 你的代码执行函数，把结果发回模型，模型用自然语言给出最终答复             |

工具定义用 JSON Schema 描述"函数叫什么、有哪些参数、参数什么类型、哪些必填"。模型靠这份 schema 和参数的 `description` 来决定**调不调、调哪个、怎么填参数**——所以工具描述写得清不清楚，直接决定调用准不准。

### 2.3 并行工具调用（Parallel Tool Calling）

面试高频考点："用户一句话要查三个城市的天气怎么办？"

现代模型支持在**一轮里同时返回多个 `tool_calls`**。你的代码可以**并发执行**它们，再把多个结果一起回填，省掉多轮往返。这是压低工具调用延迟的标准手段之一——面试官问"怎么优化 Agent 延迟"，并行工具调用就是标准答案。

### 2.4 可靠性：strict mode 接上结构化输出

怎么保证模型抽出的参数一定合法、不缺字段？这里和上一节的结构化输出直接打通：新模型支持 **strict mode（严格模式）**，开启后模型生成参数时被 schema 死死约束（约束解码），类型、必填项一个都不会错。**结构化输出不是孤立知识点，它正是工具调用可靠性的地基。**

### 2.5 安全：把模型输出当成不可信输入

资深岗位的加分意识：**模型输出的参数，本质是不可信的外部输入**。模型让你"删文件""转账"，能闭眼执行吗？绝对不能。工具调用必须：

- **参数校验**：用 Pydantic 等校验类型、范围、白名单；
- **权限控制**：工具能力最小化，敏感操作单独鉴权；
- **人工确认**：危险/不可逆操作（删除、支付、发送）加 human-in-the-loop 确认。

一句话：**把模型输出当成用户输入来防**。这能让面试官觉得你真在生产环境踩过坑。

## 三、代码示例

### 示例 1：完整的三轮对话闭环（OpenAI）

```python
import json
from openai import OpenAI

client = OpenAI()

# —— 工具定义：用 JSON Schema 描述函数 ——
tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "查询指定城市的实时天气",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "城市名，如 北京"},
                "unit": {"type": "string", "enum": ["c", "f"], "description": "温度单位"},
            },
            "required": ["city"],
        },
    },
}]

# —— 真正执行函数的是你的代码 ——
def get_weather(city: str, unit: str = "c") -> str:
    return f"{city} 晴 26°{unit.upper()}"   # 真实场景调天气 API

messages = [{"role": "user", "content": "北京今天天气怎么样？"}]

# 第 1 轮：发问（带上工具）
resp = client.chat.completions.create(model="gpt-4o", messages=messages, tools=tools)
msg = resp.choices[0].message

# 第 2 轮：模型返回 tool_calls（它只是"想调"，没真调）
if msg.tool_calls:
    messages.append(msg)
    for call in msg.tool_calls:
        args = json.loads(call.function.arguments)
        result = get_weather(**args)              # ← 你的代码执行
        messages.append({
            "role": "tool",
            "tool_call_id": call.id,
            "content": result,
        })
    # 第 3 轮：回填结果，模型给自然语言答复
    final = client.chat.completions.create(model="gpt-4o", messages=messages)
    print(final.choices[0].message.content)
```

**工程要点**：注意 `get_weather(**args)` 这一行才是真正执行——模型只给出 `arguments` 字符串，执行权牢牢在你手里。`tool_call_id` 用来把结果对应回正确的调用。

### 示例 2：并行工具调用 + 并发执行

```python
import json, asyncio
from openai import OpenAI

client = OpenAI()

async def run_tool(call):
    args = json.loads(call.function.arguments)
    # 模拟异步 IO（真实场景是 await 调外部 API）
    await asyncio.sleep(0.1)
    return {"tool_call_id": call.id, "role": "tool",
            "content": f"{args['city']} 晴 26°C"}

async def main(messages, tools):
    resp = client.chat.completions.create(model="gpt-4o", messages=messages, tools=tools)
    msg = resp.choices[0].message
    if not msg.tool_calls:
        return msg.content
    messages.append(msg)
    # 多个 tool_calls 并发执行，而不是一个个串行等
    results = await asyncio.gather(*[run_tool(c) for c in msg.tool_calls])
    messages.extend(results)
    final = client.chat.completions.create(model="gpt-4o", messages=messages)
    return final.choices[0].message.content

# 用户："北京、上海、广州天气如何" → 模型一轮返回 3 个 tool_calls
# asyncio.run(main(messages, tools))  并发执行，延迟≈单次而非3次
```

**工程要点**：模型一轮返回多个 `tool_calls`，用 `asyncio.gather` 并发执行，把"串行 3 次往返"压成"并发 1 批"，这是优化延迟的核心招式。

### 示例 3：安全护栏——参数校验 + 危险操作人工确认

```python
from pydantic import BaseModel, field_validator

DANGEROUS = {"delete_file", "transfer_money", "send_email"}

class ToolCallArgs(BaseModel):
    """对模型输出的参数做强校验，当成不可信输入"""
    path: str

    @field_validator("path")
    @classmethod
    def must_be_safe(cls, v: str) -> str:
        if ".." in v or v.startswith("/"):   # 防目录穿越/绝对路径
            raise ValueError(f"非法路径: {v}")
        return v

def execute_tool(name: str, raw_args: dict, registry: dict, confirm=lambda n, a: False):
    # 1) 校验：模型参数先过 Pydantic
    if name == "delete_file":
        args = ToolCallArgs(**raw_args)
        raw_args = args.model_dump()
    # 2) 危险操作：强制人工确认
    if name in DANGEROUS and not confirm(name, raw_args):
        return f"操作 {name} 被用户拒绝，已取消"
    # 3) 权限/存在性检查后再执行
    if name not in registry:
        raise PermissionError(f"未注册或无权限的工具: {name}")
    return registry[name](**raw_args)

# confirm 在生产里弹窗给用户点确认；这里演示直接拒绝
print(execute_tool("delete_file", {"path": "tmp.log"},
                   registry={"delete_file": lambda path: f"已删 {path}"},
                   confirm=lambda n, a: False))
```

**工程要点**：三道闸——参数校验（Pydantic）、危险操作人工确认（human-in-the-loop）、工具白名单/权限。把模型输出当攻击面来防，是生产级 Agent 的基本素养。

## 五、小结与下节预告

这节我们把 Agent 的"手"装上了。核心带走三点：**模型不执行函数**，它只输出结构化调用请求，干活的是你的代码，流程是"发问→抽参→回填"三轮闭环；**并行工具调用**能在一轮里调多个函数，是压延迟的利器；参数靠 **strict mode + 校验**保证合法，更要做**权限与人工确认**，把模型输出当不可信输入来防。

到这里，我们已经凑齐了 Agent 的所有零件——会思考（CoT/Prompt）、能结构化输出、能调工具。但把这些零件按什么方式组装起来，才算一个真正的 **Agent**？它和我们写惯的 Workflow、Chain 到底差在哪？下一节正式回答这个最根本的问题——**什么是 Agent**。这是整门课从"内功"迈向"范式"的分水岭。

## 六、练习题参考答案

<details>
<summary>点击展开 A 类参考要点</summary>

**A1.** 错在"模型调用了接口"。模型不执行任何函数，它只生成一个结构化的 `tool_call`（函数名 + 抽取的参数），真正调用接口/执行函数的是应用程序代码。正确表述：模型决定调用哪个工具并抽出参数，由我的代码执行并回填结果。

**A2.** ①发问：我把工具定义（JSON Schema）+ 用户问题发给模型；②抽参：模型返回 `tool_calls`，含函数名与从问句抽出的参数，不直接回答；③回填：我的代码执行函数，把结果以 role=tool 发回模型，模型用自然语言给最终答复。

**A3.** 模型在一轮里同时返回多个 `tool_calls`，应用可并发执行后一起回填。主要解决多次独立工具调用的延迟问题，把多轮串行往返压成一批并发。

**A4.** strict mode 在生成工具参数时用 schema 做约束解码，本质就是结构化输出。结构化输出保证参数类型/必填合规，工具调用才不会因参数错误失败，所以它是可靠性的地基。

</details>

<details>

**B2.** 在 `if msg.tool_calls:` 后加 `else: return msg.content`——模型未触发工具时直接把它的文本回答返回，不进入执行循环。

<details>
<summary>点击展开 C 类回答要点</summary>

**C1.** 模型不执行函数。它只输出一个结构化的 tool_call（函数名+参数），我的代码负责执行并回填。完整是三轮：发问（带工具定义）→ 模型返回 tool_calls 抽参 → 我执行后回填，模型再给自然语言答复。强调"模型动嘴、代码动手"。

**C2.** 利用并行工具调用：模型一轮返回多个 tool_calls，我用异步并发（asyncio.gather）同时执行再一起回填，把 N 次串行往返压成一批并发，延迟从 N×单次降到≈单次。再叠加缓存、超时控制进一步优化。

**C3.** 三道护栏：①参数校验，模型输出先过 Pydantic 校验类型/范围/路径白名单（防目录穿越等）；②权限控制，工具能力最小化、敏感工具单独鉴权；③危险/不可逆操作（删除、支付、发送）加 human-in-the-loop 人工确认。核心理念：把模型输出当成不可信的外部输入来防。

</details>
