先问你一道几乎每个 Agent 岗位都会考的题：你说你做过 Function Calling，那我问你——模型到底有没有真的去执行那个函数？很多人张口就说"模型调用了天气接口"，这一句话就暴露了你没搞懂原理，当场减分。今天这节，我们就把这套机制从里到外拆清楚，让你能答到点子上。

上一节我们让模型能稳定吐出结构化数据了。可光会抽参数还不够，模型到底怎么"决定"该调哪个函数、又怎么把自然语言里的信息精准填进参数？这一节，就是 Agent 真正长出"手"的那一刻。

先把那个最关键的误区破掉：模型自己从来不执行任何函数。它干的事只有一件——输出一个结构化的"调用请求"，告诉你"我想调 get_weather 这个函数，参数是城市等于北京"。真正去执行这个函数、去查接口、去跑代码的，是你的应用程序。模型只负责动嘴，干活的是你的代码。这一点想清楚了，面试基本就过半了。

那完整流程是怎么走的？记住它本质是三轮对话。第一轮，你把工具定义和用户问题一起发给模型，工具定义就是用 JSON Schema 描述"这个函数叫什么、有哪些参数、参数是什么类型"。第二轮，模型不直接回答，而是返回一个 tool_calls，里面是它想调的函数名和它从你这句话里抽出来的参数。第三轮，你的代码执行完函数，把结果再发回给模型，模型这才用自然语言给出最终答复。发问、抽参、回填,三轮闭环。

讲到这你可能会想，那要是用户一句话里要查三个城市的天气呢？这就引出一个高频考点，叫并行工具调用,parallel tool calling。现代模型能在一轮里同时返回多个 tool_calls，你的代码可以并发执行它们，再把结果一起回填，省掉好几轮往返，延迟一下就压下来了。面试官问你怎么优化工具调用的延迟,这就是标准答案之一。

那怎么保证模型抽出来的参数一定合法、不缺字段呢？这就接上了我们上一节讲的结构化输出。新一点的模型支持一个叫 strict mode 严格模式的开关，开了之后，模型生成参数时会被 schema 死死约束，类型、必填项一个都不会错。看，结构化输出不是孤立的知识点，它正是工具调用可靠性的地基。

最后必须提一句安全,这也是资深岗位的加分项。模型输出的参数,本质上是不可信的外部输入。它让你删个文件、转个账,你能闭着眼执行吗？绝对不能。工具调用一定要做参数校验、权限控制,危险操作还得加人工确认。把模型的输出当成用户输入来防,这个意识能让面试官觉得你真在生产环境踩过坑。

所以这一节你带走三句话。第一，模型不执行函数，它只输出结构化的调用请求，干活的是你的代码,流程是发问、抽参、回填三轮闭环。第二，并行工具调用能在一轮里调多个函数，是压延迟的利器。第三，参数要靠 strict mode 加校验保证合法，更要做权限和安全控制，把模型输出当成不可信输入来防。

我们现在已经凑齐了 Agent 的所有零件——会思考、能结构化输出、能调工具。可把这些零件按什么方式组装起来，才算一个真正的"Agent"？它和我们写惯的 Workflow、Chain 到底差在哪？下一节，我们就正式回答那个最根本的问题:到底什么是 Agent。这是整门课从"内功"迈向"范式"的分水岭。
