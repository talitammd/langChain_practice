# 第29节：降本增效 — 模型路由、Prompt 缓存与延迟优化

## 一、核心认知：降本和增效常常是同一件事

大模型调用的成本结构主要由 **token 数量 × 模型单价** 决定。优化这两个变量的手段，往往也顺带优化了延迟（更少的 token、更快的小模型意味着更短的响应时间），用户体验反而会变好，而不是"降本就要牺牲体验"的对立关系。

---

## 二、杠杆一：模型路由（Model Routing）

### 2.1 核心思路

不是所有任务都需要最强最贵的模型。先对请求做难度分级，简单任务路由到便宜的小模型，只有真正需要复杂推理的步骤才调用旗舰模型。

```python
from enum import Enum
from pydantic import BaseModel


class TaskComplexity(str, Enum):
    SIMPLE = "simple"      # 意图分类、格式转换、简单问答
    MODERATE = "moderate"  # 需要一定推理但结构清晰
    COMPLEX = "complex"    # 多步推理、复杂规划、创造性写作


class ModelRouter:
    def __init__(self, classifier_llm, model_pool: dict[TaskComplexity, str]):
        self.classifier_llm = classifier_llm
        self.model_pool = model_pool
        # model_pool 示例：
        # {
        #     TaskComplexity.SIMPLE: "gpt-4o-mini",
        #     TaskComplexity.MODERATE: "gpt-4o",
        #     TaskComplexity.COMPLEX: "gpt-4o",  # 或更强的模型
        # }

    def classify_complexity(self, task: str) -> TaskComplexity:
        """用轻量分类判断任务难度，这一步本身也应该用便宜的小模型完成"""
        prompt = f"""判断以下任务的复杂度：
- simple：意图识别、格式转换、简单事实性问答
- moderate：需要综合信息但逻辑结构清晰
- complex：需要多步推理、规划或创造性生成

任务：{task}
只返回 simple / moderate / complex 其中一个。"""
        response = self.classifier_llm.invoke(prompt)
        return TaskComplexity(response.content.strip().lower())

    def route(self, task: str) -> str:
        """返回应该使用的模型名称"""
        complexity = self.classify_complexity(task)
        return self.model_pool[complexity]


# 使用示例
router = ModelRouter(
    classifier_llm=cheap_llm,
    model_pool={
        TaskComplexity.SIMPLE: "gpt-4o-mini",
        TaskComplexity.MODERATE: "gpt-4o",
        TaskComplexity.COMPLEX: "gpt-4o",
    },
)
model_name = router.route("把这句话翻译成英文")  # 大概率路由到 mini 模型
```

### 2.2 规则引擎替代分类模型（进一步降本）

如果任务类型可以通过简单规则判断（比如根据 API 路由、用户意图标签），甚至不需要额外的分类模型调用：

```python
def rule_based_route(request_type: str, model_pool: dict[str, str]) -> str:
    """用规则而不是模型调用做路由判断，连分类这一步的成本都省掉"""
    simple_types = {"format_conversion", "intent_classification", "translation"}
    if request_type in simple_types:
        return model_pool["cheap"]
    return model_pool["strong"]
```

**面试考点**：2026 年很多团队实测下来，模型路由能把整体成本压掉 40% 以上，因为真实流量分布通常是"大部分请求简单、少部分请求复杂"的长尾分布，用统一的旗舰模型处理所有请求是巨大的浪费。

## 三、杠杆二：提示词缓存（Prompt Caching）

### 3.1 问题：重复计算不变的前缀

Agent 场景里，系统提示词、工具定义描述在多轮调用之间几乎不变，只有用户的具体问题在变化：

```python
# 每次调用，这部分内容完全相同，重复计算是浪费
SYSTEM_PROMPT = """你是一个专业的客服助手，可以调用以下工具：
1. query_order(order_id) - 查询订单状态
2. process_refund(order_id, reason) - 处理退款
... （假设这里有几千字的工具描述和行为准则）
"""

# 只有这部分在变化
user_question = "我的订单什么时候发货"
```

### 3.2 利用厂商提供的缓存机制

```python
def build_cached_request(system_prompt: str, user_question: str) -> dict:
    """
    大多数主流模型厂商支持标记"可缓存"的前缀内容，
    命中缓存的部分按大幅折扣计费（甚至接近免费），
    只有新增的、变化的部分按正常价格计费。
    """
    return {
        "messages": [
            {
                "role": "system",
                "content": system_prompt,
                "cache_control": {"type": "ephemeral"},  # 标记为可缓存内容
            },
            {"role": "user", "content": user_question},
        ]
    }
```

**工程价值**：对于系统提示词很长、工具很多的 Agent 场景（比如包含几十个工具定义的复杂 Agent），提示词缓存能显著降低单次调用成本，这是几乎零代价就能拿到的优化收益，属于"配置一下就能省钱"的低垂果实。

## 四、杠杆三：精简上下文

这是第 13 节 Context Engineering 思路的成本视角延伸：

```python
class ContextBudgetManager:
    """在拼接 prompt 之前，对上下文做预算控制，而不是无脑塞入所有可用信息"""

    def __init__(self, max_context_tokens: int = 4000):
        self.max_context_tokens = max_context_tokens

    def build_context(self, retrieved_docs: list[dict], conversation_history: list[dict]) -> str:
        # 优先级：最相关的检索证据 > 最近几轮对话 > 更早的历史
        budget = self.max_context_tokens
        parts = []

        # 检索证据按相关性排序后，只取预算内能装下的部分
        for doc in sorted(retrieved_docs, key=lambda d: -d["score"]):
            doc_tokens = self._estimate_tokens(doc["content"])
            if doc_tokens > budget:
                break
            parts.append(doc["content"])
            budget -= doc_tokens

        # 剩余预算给对话历史，从最近的往前装
        for turn in reversed(conversation_history):
            turn_tokens = self._estimate_tokens(turn["content"])
            if turn_tokens > budget:
                break
            parts.insert(0, turn["content"])
            budget -= turn_tokens

        return "\n\n".join(parts)

    def _estimate_tokens(self, text: str) -> int:
        # 简化估算，真实场景用具体模型的 tokenizer 精确计算
        return len(text) // 2  # 中文场景的粗略估算
```

**双重收益**：既省钱（更少 token），又防止 lost in the middle 稀释模型注意力（第 23 节讲过塞太多不相关信息反而会让模型变笨）。定期审视 prompt 构造逻辑、砍掉不必要的信息，是一个既省钱又提升效果的动作，这也是为什么说"降本和增效常是同一件事"。

## 五、杠杆四：批处理与异步化

### 5.1 批处理 API：用延迟换成本

```python
class BatchProcessor:
    """对不要求实时响应的任务（如夜间批量生成报告），
    使用模型厂商的批处理 API，通常有显著价格折扣"""

    def __init__(self, batch_llm_client):
        self.batch_llm_client = batch_llm_client

    def submit_batch_job(self, tasks: list[dict]) -> str:
        # 批处理 API 通常异步执行，几小时后返回全部结果，
        # 换来的是相比实时 API 更低的单价
        job_id = self.batch_llm_client.submit(tasks)
        return job_id

    def poll_results(self, job_id: str) -> list[dict] | None:
        status = self.batch_llm_client.get_status(job_id)
        if status == "completed":
            return self.batch_llm_client.get_results(job_id)
        return None
```

### 5.2 并行化独立子任务

```python
import asyncio

async def process_independent_subtasks(llm, subtasks: list[str]) -> list[str]:
    """如果多个子任务之间没有依赖关系，并发调用而不是串行调用，
    整体延迟能压缩到接近单次调用的水平（阶段1学过的异步编程技术在这里复用）"""
    results = await asyncio.gather(*[llm.ainvoke(task) for task in subtasks])
    return results

# 反面对比：串行调用，总耗时是所有子任务耗时之和
```

## 六、杠杆五：模型蒸馏与微调小模型

### 6.1 适用场景

如果 Agent 里有某个**高频、模式相对固定**的子任务，长期用大模型处理是"杀鸡用牛刀"：

```python
class DistillationPipeline:
    """收集高频子任务的历史调用数据，用大模型的输出作为训练数据，
    微调一个小模型专门处理这一类任务"""

    def __init__(self, teacher_llm, training_data_store):
        self.teacher_llm = teacher_llm
        self.training_data_store = training_data_store

    def collect_training_data(self, task_type: str, num_samples: int) -> list[dict]:
        """从生产环境中收集某类高频任务的真实输入，
        用大模型（teacher）生成高质量输出作为训练标签"""
        samples = self.training_data_store.get_recent_inputs(task_type, num_samples)
        training_pairs = []
        for sample in samples:
            teacher_output = self.teacher_llm.invoke(sample["input"])
            training_pairs.append({
                "input": sample["input"],
                "output": teacher_output.content,
            })
        return training_pairs

    def export_for_finetuning(self, training_pairs: list[dict], output_path: str) -> None:
        """导出为微调所需的格式（如 JSONL），交给微调平台处理"""
        import json
        with open(output_path, "w", encoding="utf-8") as f:
            for pair in training_pairs:
                f.write(json.dumps({
                    "messages": [
                        {"role": "user", "content": pair["input"]},
                        {"role": "assistant", "content": pair["output"]},
                    ]
                }, ensure_ascii=False) + "\n")
```

**面试考点**：这个策略的适用边界是"任务模式固定、调用频率高"，如果任务本身多样且需要通用推理能力，蒸馏出的小模型效果会明显下降，这种情况不适合蒸馏，仍应该用模型路由分流到合适的通用模型。

## 七、成本监控与预算护栏

优化手段做完还需要持续监控，防止成本反弹：

```python
from dataclasses import dataclass


@dataclass
class CostBudget:
    daily_budget_usd: float
    alert_threshold_pct: float = 0.8  # 消耗到预算的 80% 就告警


class CostGuardian:
    def __init__(self, budget: CostBudget, cost_tracker, alert_sink):
        self.budget = budget
        self.cost_tracker = cost_tracker
        self.alert_sink = alert_sink

    def check_and_enforce(self) -> bool:
        """返回 False 表示应该拒绝新请求（预算已耗尽），用于极端情况下的熔断保护"""
        today_cost = self.cost_tracker.get_today_cost()

        if today_cost > self.budget.daily_budget_usd:
            self.alert_sink.send(f"今日成本已超预算：${today_cost:.2f} / ${self.budget.daily_budget_usd:.2f}")
            return False

        if today_cost > self.budget.daily_budget_usd * self.budget.alert_threshold_pct:
            self.alert_sink.send(f"今日成本接近预算上限：${today_cost:.2f}")

        return True
```

这和第 28 节讲的告警机制是同一套体系的延伸——可观测性负责"看见"，成本护栏负责在异常情况下（比如死循环导致的 token 暴增）主动熔断，避免出现"一个 bug 导致巨额账单"的极端事故。

## 八、面试高频问答

**Q：给你一个 Agent 系统，成本超预算了，你会按什么顺序排查和优化？**
A：先用可观测性数据（第28节）定位成本主要花在哪个环节——是某个高频子任务、还是某类请求的上下文过长、还是本来该用小模型的地方用了大模型。找到主要矛盾后，优先做模型路由（收益最大、改动最小），再做提示词缓存和上下文精简（几乎零副作用），最后对确实高频且模式固定的子任务考虑蒸馏微调（投入产出比要单独评估）。

**Q：模型路由会不会影响回答质量？怎么保证不会"该用大模型的地方错误地用了小模型"？**
A：这正是第27节 Eval 体系发挥作用的地方——路由策略上线前后都要跑一遍评估数据集，验证分流到小模型的那部分任务质量没有明显下降，如果某类任务在小模型上评估分数不达标，说明分类边界划错了，需要调整路由规则。

**Q：批处理 API 和实时 API 怎么选？**
A：看业务对延迟的容忍度。用户实时对话必须用实时 API；夜间跑的报表生成、批量数据标注、离线评估这类不要求即时反馈的任务，批处理 API 用延迟换取显著的价格折扣是很划算的交易。

## 十、小结

这一节讲了五个降本增效的核心杠杆：模型路由把简单任务分流给便宜模型是收益最大的一招，提示词缓存省掉重复计算的开销近乎零成本，精简上下文既省钱又防止 lost in the middle 稀释效果，批处理和并行化用架构设计换取成本和延迟的双重优化，模型蒸馏把高频固定任务的长期成本降到最低。所有优化手段最终都要接入成本监控和预算护栏，防止异常情况下的失控。
